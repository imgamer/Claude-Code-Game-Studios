## 0. 先搞清楚 Phase 边界（上一版犯的错）

### 0.1 `/map-systems` 属于 Phase 1，不是 Phase 2

[workflow-catalog.yaml](file:///workspace/.claude/docs/workflow-catalog.yaml) 是阶段顺序的**单一事实源**，它把 7 个 Phase 的边界划得清清楚楚：

```yaml
phases:
  concept:              # Phase 1
    steps:
      - brainstorm
      - engine-setup
      - game-concept
      - design-review-concept
      - art-bible
      - map-systems     # ← 在这里！Phase 1 的最后一步
    next_phase: systems-design

  systems-design:       # Phase 2
    steps:
      - design-system   # ← Phase 2 从这里开始
      - design-review
      - review-all-gdds
      - consistency-check
    next_phase: technical-setup

  technical-setup:      # Phase 3
  pre-production:       # Phase 4
  production:           # Phase 5
  polish:               # Phase 6
  release:              # Phase 7
```

**为什么上一版把 `/map-systems` 归到 Phase 2**：两个技能在工作流里紧挨着——先画总图再写 GDD。但 workflow-catalog 的划分逻辑是：**Phase 1 产出"是什么"（概念 + 总图），Phase 2 产出"怎么做"（每个系统的详细 GDD）**。`/map-systems` 做的是"把概念拆成系统清单"，属于"是什么"的延续；`/design-system` 做的是"把每个清单项写成 8 节规格"，属于"怎么做"的开始。

**初中生版类比**：`/map-systems` 是"圈地"——先画出城市要建哪些功能区、谁先建、谁后建；`/design-system` 是"出施工图"——给每个功能区画详细图纸。圈地之前你还没想好要不要建这座城（那是 Phase 1 的 brainstorm），圈地之后才能开始逐栋出施工图。

### 0.2 为什么要讲 Phase 1 的 `/map-systems` 机制？

你问的显式+隐式推断、依赖五层、TD-SYSTEM-BOUNDARY 门禁——全在 `/map-systems`（Phase 1）里。但 Phase 2 的入口就是 `/map-systems` 的产物（systems-index.md），而且 TD-SYSTEM-BOUNDARY 门禁的判决**直接决定 Phase 2 要不要改系统边界重写 GDD**。所以：

- **Phase 1 详解**（枚举、依赖、门禁）：§1-§3 深入你指定的三个机制；
- **Phase 2 详解**（骨架、逐节写、会话隔离评审）：§4-§5 深入 Phase 2 的核心机制。

## 1. `/map-systems` 枚举机制详解：显式 + 隐式

### 1.1 显式提取：从概念文档四个固定位置扫

技能源码（[map-systems/SKILL.md 第 109-115 行](file:///workspace/.claude/skills/map-systems/SKILL.md#L109-L115)）规定了**四个必须扫的位置**，顺序不能换：

|------|--------|--------------------------|
| Core Mechanics | 游戏核心玩法的机制描述 | 最直接——"玩家扔炸弹"→ 炸弹系统 |
| Core Loop | 每一层循环的驱动因子 | 循环暗示驱动力："跑砍怪捡宝"→ 砍击系统、掉落系统 |
| Technical Considerations | 技术要求 | "需要联机"→ 网络层、匹配系统 |
| MVP Definition | 必备功能列表 | 必备功能=必备系统，反推遗漏 |

**技术细节**：不用全文读——先用 Grep 找 `^#` 标题定位，再用 offset/limit 只读这四个段落。概念文档可能几十 KB，全文读浪费上下文。

### 1.2 隐式推断：技能内置的推断模式（关键机制）

这是 `/map-systems` 最容易被低估的部分——概念文档**永远不会**列全所有系统。技能内置了 6 组推断模式（[第 119-136 行](file:///workspace/.claude/skills/map-systems/SKILL.md#L119-L136)），每组都是一个"已知系统 → 隐含系统"的映射表：

#### 模式一：Inventory（背包）隐含的 5 个系统

```
你写了 Inventory（背包）
  ├─ Item database（物品数据库）   —— 背包里能放什么？需要一张物品清单
  ├─ Equipment slots（装备槽）     —— 不是所有物品都能放背包，有些要挂身上
  ├─ Weight/capacity rules（重量规则）—— 背包为什么会满？不能无限装
  ├─ Inventory UI（背包界面）     —— 玩家怎么打开、拖拽、排序
  └─ Item serialization（存档序列化）—— 关游戏再开，背包要原样回来
```

**推断逻辑**（通用模板）：

```
一个"显式系统 X" = 玩家和/或代码能感知到的功能
        ↓
必然隐含 "X 内部需要的数据结构"（比如物品清单）
+ "X 对外暴露的交互界面"（比如拖拽）
+ "X 持久化需要的序列化"（比如存档）
+ "X 的细分变体"（装备槽 vs 背包格）
```

#### 模式二：Combat（战斗）隐含的 7 个系统

```
Combat（战斗）
  ├─ Damage calculation（伤害计算）  —— 打一下扣多少
  ├─ Health system（血量系统）       —— 怎么知道死了
  ├─ Hit detection（命中判定）       —— 打没打到
  ├─ Status effects（状态效果）      —— 中毒、眩晕
  ├─ Enemy AI（敌人 AI）             —— 敌人怎么反应
  ├─ Combat UI（战斗界面）           —— 血条、伤害数字
  └─ Death/respawn（死亡/重生）      —— 死了怎么办
```

#### 模式三：Open World（开放世界）隐含的 6 个系统

```
Open World（开放世界）
  ├─ Streaming/chunking（流式加载） —— 地图太大，不能一次性全加载
  ├─ LOD system（细节层次）          —— 远处的东西不用画那么细
  ├─ Fast travel（快速旅行）         —— 玩家不可能走遍每一寸
  ├─ Map/minimap（地图/小地图）      —— 玩家怎么认路
  ├─ Point of interest tracking（兴趣点追踪）—— 哪些地方值得去
  └─ World state persistence（世界状态持久化）—— 砍过的树不能长回来
```

#### 模式四：Multiplayer（联机）隐含的 5 个系统

```
Multiplayer（联机）
  ├─ Networking layer（网络层）       —— 数据怎么传输
  ├─ Lobby/matchmaking（大厅匹配）   —— 玩家怎么聚到一起
  ├─ State synchronization（状态同步）—— 服务器和客户端状态要一致
  ├─ Anti-cheat（反作弊）            —— 有人开挂怎么办
  └─ Network UI（网络界面）          —— 延迟、玩家列表
```

#### 模式五：Crafting（合成）隐含的 5 个系统

```
Crafting（合成）
  ├─ Recipe database（配方数据库）   —— 哪些原料能合出什么
  ├─ Ingredient gathering（原料采集）—— 原料从哪来
  ├─ Crafting UI（合成界面）         —— 玩家怎么操作
  ├─ Success/failure mechanics（成败机制）—— 合成会不会失败
  └─ Recipe discovery/learning（配方发现）—— 配方怎么获得
```

#### 模式六：Progression（成长）隐含的 6 个系统

```
Progression（成长）
  ├─ XP system（经验系统）           —— 怎么涨经验
  ├─ Level-up mechanics（升级机制）  —— 满了之后怎么办
  ├─ Skill tree（技能树）            —— 点什么技能
  ├─ Unlock tracking（解锁追踪）     —— 哪些解锁了
  ├─ Progression UI（成长界面）      —— 玩家怎么看进度
  └─ Progression save data（成长存档）—— 成长状态存哪
```

### 1.3 为什么显式+隐式要分开做

**显式系统**是概念文档里**你主动写的**，代表"你已经想清楚这游戏要什么了"；**隐式系统**是"你写了 X，但没有 X 背后的支撑系统，X 根本跑不起来"。分开做的好处：

1. **让你能判断推断是否过度**——概念文档里没有"反作弊"，一个 2D 解谜游戏也不需要反作弊。推断模式只是**候选清单**，用户评审时可以砍掉；
2. **在对话里解释每个隐式系统为什么需要**——AI 不能只甩给你一张表，必须给出推断依据（"背包需要物品数据库，因为没有它背包里能放什么就没法约束"），让你能判断它推得对不对；
3. **强制覆盖存档和 UI 两类"隐形刚需"**——几乎每个系统都需要序列化和对应 UI，但概念文档几乎从不提它们。推断模式把这两类**统一补进清单**。

**误区预警**：隐式推断**不是自动加**——用户评审时三个问题（有漏？合并/拆？不需要？）就是纠偏入口。collaborative 模式反复问到你满意为止；guided 只问一次；autonomous 不问但要用 `log_decision` 记录推断依据。

## 2. 依赖五层 + 循环依赖检测：实现逻辑

### 2.1 为什么要做依赖分层（核心逻辑）

**一个朴素的问题**：为什么不按"实现顺序"直接排？因为实现顺序有两个陷阱：

1. **依赖环**：A 需要 B 的数据结构，B 又需要 A 的状态——谁先写谁都是半成品；
2. **隐式依赖**：战斗系统写了一半发现需要"玩家生命值"这个东西，但生命值系统没人设计——它被当成了战斗的内部组件，而不是独立的系统。

依赖分层把"实现顺序"问题转化为"拓扑排序"问题——**一个系统能在第几层被设计，完全由它依赖谁决定**，和它的业务领域无关。

### 2.2 三层依赖判定启发式（技能规定的识别方法）

[map-systems SKILL.md 第 166-170 行](file:///workspace/.claude/skills/map-systems/SKILL.md#L166-L170) 规定了**三种"依赖"定义**：

| 依赖类型 | 含义 | 判定问题 | 例子 |
|----------|------|----------|------|
| **输入/输出依赖** | A 产出 B 需要的数据 | "B 能不能在没有 A 输出的情况下运行？" | 掉落系统（产出掉落包）→ 背包系统（消费掉落包） |
| **结构依赖** | A 提供 B 插入的框架 | "B 能不能在没有 A 提供的接口的情况下被访问？" | 事件总线（提供信号机制）→ 一切用信号通信的系统 |
| **UI 依赖** | UI 系统是玩法系统的"展示层" | "玩法系统有没有一个对应的 UI 让玩家能交互？" | 战斗系统 → 战斗 HUD（血条、伤害数字） |

**注意 UI 依赖的特殊性**：每个玩法系统必然拖着一个 UI 系统，但**UI 排在玩法之后设计**——因为 UI 要知道玩法有什么状态（比如血条要知道血量从哪来）。这就是为什么 UI 层（Presentation）排在 Core/Feature 之后。

### 2.3 五层排序算法（朴素拓扑排序的简化版）

技能没有写死一个脚本算法（因为这部分由大模型推理完成，不是 awk），但规则是固定的：

```
从"没有任何依赖"的系统开始 → 放进 Foundation 层
从剩余系统里挑"只依赖 Foundation"的 → 放进 Core 层
从剩余系统里挑"只依赖 Foundation/Core"的 → 放进 Feature 层
从剩余系统里挑"UI 依赖某个已在 Core/Feature 的玩法系统"的 → 放进 Presentation 层
剩下的（教程、埋点、无障碍、元系统） → Polish 层
```

**技术细节**：这就是经典的**拓扑排序（Kahn 算法）**——每轮移除入度为 0 的节点，放入当前层。如果一轮下来没有任何入度为 0 的节点被移除，说明有环。

### 2.4 循环依赖检测与三种解法

技能第 183-186 行规定：检测到环时**高亮给用户**，并提出三种解法——

| 解法 | 什么时候用 | 例子 |
|------|-----------|------|
| **接口抽象（抽第三方）** | A 和 B 互相需要对方的某个子集 | 战斗需要玩家状态、玩家状态需要战斗结果 → 抽出 `EventBus`，战斗发"伤害事件"，玩家状态监听更新血量，两者不再互相 import |
| **同步设计** | 环很小且确实紧密耦合 | 对话系统和角色状态系统需要同时敲定对话影响的属性 → 在同一轮 `/design-system` 里把两个系统的 GDD 一起写 |
| **定义合同后各自独立** | 环可以被打破，但需要先约定接口 | 背包系统和经济系统都需要"物品价格" → 先约定 `registry.sh slice design/registry/entities.yaml` 是双方的价格来源，然后各自设计 |

**为什么检测要在总图阶段做**：循环依赖拖到写代码时才暴露，代价是**架构级返工**——两个系统的模块要重写、测试要重写。但在总图阶段发现，改一行表格就行。这就是"缺陷发现越早修复代价越小"的 shift-left 原理的直接体现。

### 2.5 瓶颈系统 vs 叶子系统（风险识别）

依赖图里**入度最高**（被最多系统依赖）的是瓶颈系统——它写坏了，下游全挂；**出度为 0**（不依赖任何其他系统）的是叶子系统——它可以独立设计、独立测试。两者都要在总图里高亮：

- 瓶颈系统（"许多 others depend on them — these are high-risk"）：应该**更早设计、更仔细评审**；
- 叶子系统（"no dependents — lower risk, can be designed late"）：可以**晚设计、简化 GDD**，不阻塞 MVP。

## 3. TD-SYSTEM-BOUNDARY：为什么在写 GDD 之前评审

### 3.1 先看门禁实际检查什么

[td-system-boundary.md](file:///workspace/.claude/docs/director-gates/td-system-boundary.md) 是一个独立的门禁定义文件，由被召唤的 `technical-director` 智能体**自己读**——主会话不读它。门禁的 Prompt 原文是：

> "Review this systems decomposition from an architectural perspective before GDD authoring begins. Are the system boundaries clean — does each system own a distinct concern with minimal overlap? Are there God Object risks (systems doing too much)? Does the dependency ordering create implementation-sequencing problems? Are there implicit shared-state problems in the proposed boundaries that will cause tight coupling when implemented? Are any Foundation-layer systems actually dependent on Feature-layer systems (inverted dependency)? Return APPROVE / CONCERNS / REJECT."

**五个具体问题**（每个都对应一种在 GDD 里改不动的架构病）：

| 问题 | 检测什么 | 对应架构病 |
|------|----------|-----------|
| 边界干净吗？ | 每个系统是不是管一件独立的事 | 职责重叠：战斗系统也写了装备逻辑、背包系统也写了重量计算 |
| 有 God Object 风险吗？ | 一个系统是不是管了超过 3 件不同领域的事 | "GameManager" 同时管存档、场景切换、UI 状态、玩家数据 |
| 依赖顺序会不会造成实现问题？ | 会不会出现"我依赖的系统还没设计，我需要猜它的接口" | 网络系统写了一半，发现匹配大厅的接口没人定义 |
| 有没有隐式共享状态？ | 两个系统是不是都偷偷读/写同一个全局变量 | 血量系统和受伤系统都直接改 `player.health`，没有 owner |
| 有没有反向依赖？ | Foundation 层的系统是不是反过来依赖 Feature 层 | 事件总线（Foundation）的实现里 import 了战斗系统（Feature）的类型 |

### 3.2 为什么必须在写 GDD 之前做（代价对比）

这个门禁的设计初衷就是**代价不对称**——让我们算一笔账：

**场景**：总图有问题，一个系统边界划错了（比如把装备逻辑挂在了战斗系统下，而不是独立成装备系统）。

| 时机 | 修复动作 | 修复代价 |
|------|----------|----------|
| **写 GDD 之前**（TD-SYSTEM-BOUNDARY 在这跑） | 在 systems-index.md 里把"装备"从战斗的子项改成独立系统；依赖图里加一条"战斗依赖装备" | **改 1 张表 + 1 张依赖图**，5 分钟 |
| **写完所有 GDD 之后**（假设没这门禁，直接进写阶段） | 战斗 GDD 里所有涉及装备的章节（伤害计算、命中判定、状态效果）都要重写或拆出去；装备 GDD 要从零开始写；所有引用了战斗→装备接口的兄弟 GDD 都要改 | **改 5-10 份 GDD**，几小时；如果已经开始写代码，架构级返工，几天 |

**shift-left 原理在 AI 工作流里的具体落地**：AI 写文档比人快，但 AI 返工也比人快不多少（因为返工要理解历史决策、重新论证取舍、更新所有下游引用）。**让返工的对象越少越好**——表格返工 < GDD 返工 < 代码返工。

### 3.3 为什么门禁文件由被召唤的智能体自己读

主会话里有大量"系统枚举、依赖映射、优先级分配"的上下文——这些是 AI 在前面阶段推理的产物。如果主会话**自己读了 td-system-boundary.md 然后转述给 technical-director**，有两个风险：

1. **信息损耗**：主会话转述会丢失"为什么这个循环依赖被标记为已解决"这类推理细节；
2. **上下文膨胀**：主会话要同时维护枚举、依赖、优先级、门禁规则四套上下文，容易让后续决策变糙。

所以技能规定：**主会话只传"文件路径 + 依赖图 + 分层 + 循环依赖"这五份数据**，门禁定义文件由 technical-director 自己 Read——主会话只负责召唤和接收判决。这是项目"**能外包的读取不占主会话上下文**"这条上下文经济学原则的具体体现。

## 4. Phase 2 详解：`/design-system` 的骨架与逐节设计

Phase 2 从 `/design-system` 开始，到 `/consistency-check` 结束。它的入口是 Phase 1 产出的 systems-index.md（包含每个系统的 Category、依赖、优先级、设计顺序）。

### 4.1 先建空骨架（§3）：为什么先写空文件再逐节填

[3-file-skeleton.md](file:///workspace/.claude/skills/design-system/references/3-file-skeleton.md) 明确规定："**Once the user confirms, immediately create the GDD file with empty section headers**"——用户批准后**立刻**创建完整空骨架。

三个核心理由（按重要性排序）：

#### 理由一：断点锚——文件存在了才能从断点恢复

`design-system` 的 §7（Recovery & Resume）明确：会话中断后，恢复逻辑的第一步是**读文件按节判断完成度**——"有真内容的节=完成，`[To be designed]`=待做"。如果骨架没有先建，恢复逻辑就没法判断"应该有哪些节"——它不知道 8 节都应该存在还是 4 节，也不知道哪些是"应该有但还没写"、哪些是"根本不需要"。

**这是"增量写入=抗中断"的前提**：每节批准即落盘，任何中断最多损失"正在讨论的那一节"。但增量写入的前提是**有一个已经存在的文件来承载增量**——没有骨架，每节都要从零创建文件，断点恢复的锚就丢了。

#### 理由二：消费方可探测——空骨架也是有效的进度信号

骨架一建好，三个下游消费者立刻有东西读：

| 消费者 | 读什么 | 空骨架给出的信号 |
|--------|--------|------------------|
| `gdd-structure-check.sh` | 按标题名扫描文件 | 8 节骨架 = "结构齐全"；`[To be designed]` 占位符 = "内容未填充" |
| `review-scope.sh` | 按文件名匹配 systems-index | "combat.md 已存在" → 进度条 +1，即使全是空的 |
| `/consistency-check` | 对比注册表和 GDD 值 | "有 combat.md" → 开始扫描值，发现占位符就是"值未定义" |

**为什么这很重要**：在 `workflow: full` 下，`/create-epics` 会按 systems-index 里的设计顺序**逐个 GDD** 创建史诗——它需要知道每个 GDD 是否"存在"来判断当前 phase。空骨架也算"存在"，否则它会一直卡在前一个 GDD 没写完的状态。

#### 理由三：用户可见全景——先看到 8 个标题再逐个填

用户先看到 8 个章节标题（Overview / Player Fantasy / Detailed Design / Formulas / Edge Cases / Dependencies / Tuning Knobs / Acceptance Criteria），对"这份 GDD 会包含什么、不会包含什么"有明确预期。逐节填充时不会迷失——"哦，Edge Cases 节写过了，不用再写了"。

**反模式**：一次性生成整份 GDD 让用户追认。技能明令禁止（"Never auto-generate the full GDD and present it as a fait accompli"），因为用户看到一份完整的文档会产生"我已经批准了"的错觉，但实际上他只批准了"逐节写"这个流程。

### 4.2 骨架只建"当前档位要求的节"——不做多余占位

3-file-skeleton.md 明确规定：骨架**只 scaffold 当前 workflow 档位要求的节**。具体规则：

| workflow 档位 | 骨架包含的节 | 省略的节 |
|---------------|-------------|---------|
| `full` | 全部 8 节 + Game Feel | 无 |
| `standard` | Overview / Detailed Design / Edge Cases / Dependencies / Acceptance Criteria + Formulas（条件：系统有数值规则时） | Player Fantasy / Tuning Knobs（除非 workflow_overrides 强制） |
| `minimal` | 可选（GDD 不是必需产物） | 完整 8 节清单可以按需省略 |

**关键细节**：被省略的节**不留占位符**——它们根本不存在于骨架里。技能特意警告："Do not leave empty `[To be designed]` placeholders for those"——因为 §4 的"Section Cycle"只会遍历骨架里**实际存在**的节。如果你手动往骨架里加了一个 Player Fantasy 节（standard 档不要求的），§4 也会尝试写它，而你还会被问一堆关于 Player Fantasy 的问题，白白浪费 token 和时间。

## 5. 会话隔离：怎么保证 `/design-review` 的独立性

### 5.1 为什么必须新会话跑设计评审

[design-system SKILL.md 第 120-124 行](file:///workspace/.claude/skills/design-system/SKILL.md#L120-L124) 有一句关键的禁令：

> "§5c forbids offering `/design-review` inline, because the reviewing agent must not inherit this session's design history."

"inherit this session's design history" 是指什么？一个会话（session）在 Claude Code 里就是**一个连续的对话历史**。如果你在同一个会话里先跑 `/design-system combat`（写战斗 GDD），然后紧接着跑 `/design-review design/gdd/combat.md`（评审战斗 GDD），评审者（可能是同一个模型，也可能是召唤的子智能体）会：

1. **知道你为什么写了这个公式**（你刚才说"暴击率 20% 够了"）；
2. **知道你否定了什么**（你刚才考虑过 15% 但嫌太低）；
3. **知道你犹豫过什么**（你刚才说"Edge Cases 是不是真的需要写这么多"）。

这些是**作者的辩护词**，不是文档本身的内容。一个知道作者辩护词的评审者，天然倾向于**给面子、放过弱点**——"他刚才想了这么久才定 20%，应该有道理吧"。但"应该有道理"≠"真的有道理"，一个独立评审应该只面对**最终文档**，不面对**决策过程**。

### 5.2 这个项目怎么做到会话隔离

| 层 | 机制 | 怎么隔离 |
|----|------|----------|
| **技能层**（最根本） | `design-system` §5c **禁止内联提供** `/design-review` 作为选项 | 技能在收尾时的"下一步"选项里**根本没有**"跑设计评审"，只指引用户"在新会话跑" |
| **会话层**（物理隔离） | 用户必须**开新终端 / 新会话** | 新会话的历史是干净的——没有设计过程、没有决策讨论、没有作者的辩护词。它 Read 进上下文的只有 GDD 本体、CLAUDE.md、注册表 |
| **指纹层**（保证评审的就是这版） | `/design-review` Phase 1 第一步先跑 `review-receipts.sh check` | 新会话不知道"你改过什么"，但指纹对比能让它知道"这版 GDD 和上次评审的是不是同一版"——如果是就直接复用判决，如果不是就全量评审 |
| **门禁层**（新会话内的隔离） | `design-review` Phase 1 的"Freshness check first" | 即使同一个评审者被复用，它在新会话里也必须**先验指纹再决定要不要审**——它不能跳过这个步骤因为它"知道文档是自己刚写的"（它根本不知道，历史被隔离了） |

### 5.3 技能明文禁止的两种"省事"做法

design-system SKILL.md 第 149-151 行的 Recommended Next Steps 明确写着：

> "Run `/design-review design/gdd/[system-name].md` in a **fresh session** to validate the completed GDD independently."

而 Collaborative Protocol 里重申了："§5c forbids offering `/design-review` inline, because the reviewing agent must not inherit this session's design history."

**两种被禁止的"省事"做法**：

| 做法 | 为什么被禁止 | 正确做法 |
|------|-------------|---------|
| 在同一个会话里先 `/design-system` 再 `/design-review` | 评审者继承了作者的辩护词，独立性破坏 | 开新会话 |
| `/design-review` 里只审"变了的章节"（章节级偷懒） | "没变"只说明字节和上次一样，不说明上次评审全面 | 全量评审（design-review 明令禁止 delta re-review，见 design-review SKILL.md 第 96-102 行） |

### 5.4 哈希回执和会话隔离的配合（一个容易忽略的细节）

在新会话里跑 `/design-review` 时，评审者是"盲的"——它不知道这份 GDD 是刚写完的还是改了五版的。哈希回执就是它的"眼睛"：

```
新会话启动 → /design-review combat.md
  → Phase 1: review-receipts.sh check
    → 发现 combat.md 是 NEW（从未被盖过章）→ 全量评审
    → 或者发现 combat.md UNCHANGED、上一次判决是 APPROVED → 直接复用旧判决
    → 或者发现 combat.md CHANGED、上一次判决是 NEEDS REVISION → 重新评审
```

**为什么新会话里也能复用旧判决**：因为指纹只看内容不看会话历史。两个会话、两个时间点、两个完全不同的上下文，只要内容一样，判决就可以一样——这就是指纹把"评审独立性"和"评审可复用性"这两个看似矛盾的目标同时实现的方式。

## 7. 设计思路对照表（为什么这么做）

| 设计选择 | 直接原因 | 深层原理 |
|----------|----------|----------|
| `/map-systems` 属于 Phase 1 不是 Phase 2 | 它产出的是"是什么"的清单，不是"怎么做"的规格 | **Phase 边界 = 交付物类型**：概念+总图=Phase 1，施工图=Phase 2 |
| 枚举分显式+隐式 | 概念文档必然漏系统 | **把未来的惊吓变成现在的清单** |
| 依赖分五层+循环检测 | 依赖决定实现顺序 | **拓扑排序**思想；shift-left（循环依赖拖到代码里=架构级返工） |
| TD-SYSTEM-BOUNDARY 在写 GDD 之前 | 表格改边界是分钟级，30 份 GDD 返工是天级 | **代价不对称**：缺陷越早发现，修复代价指数级下降 |
| 门禁文件由被召唤的智能体自己读 | 主会话转述有损且耗上下文 | **上下文经济学**：能外包的读取不占主会话 |
| 先建空骨架 | 断点锚 + 消费方可探测 + 用户见全景 | **增量写入=抗中断**的前提；空骨架是有效进度信号 |
| 骨架只建档位要求的节 | 多余占位符会让 §4 尝试写不存在的节 | **消费方按骨架遍历**，骨架外的节永远不会被写 |
| 禁止内联 `/design-review` | 评审者不能继承作者的辩护词 | **会话隔离=评审独立性** |
| `/design-review` 验章优先于通读 | 同一版文档重复评审浪费 | **指纹把独立性和可复用性同时实现** |
| 禁止章节级偷懒重审 | "没变"≠"上次审得全面" | **安全优先**：宁可多审一次，不可放过缺陷 |
| 注册表优先于兄弟 GDD | GDD 可能漂移，注册表是单一事实源 | **单一事实源**原则的具体落地 |

## 9. 常见误区

1. **"/map-systems 就是 Phase 2 的事"**。错。workflow-catalog 把它放在 Phase 1（Concept）的最后一步，Phase 2 从 `/design-system` 开始。分界点：Phase 1 产出"是什么"（概念+总图），Phase 2 产出"怎么做"（施工图）。
2. **"隐式推断的系统我必须接受"**。不是。显式+隐式之后有用户评审（三个问题：漏？合并/拆？不需要？），三个 automation 档位对"要不要问"的要求不同，但**不会自动加**。
3. **"依赖五层是固定模板，所有游戏都套"**。不是。分层规则（Foundation 无依赖、Foundation→Core→Feature 单向）是固定的，但**哪些系统属于哪层**是推理出来的——一个 2D 解谜游戏没有 Networking 层的隐式系统，它的依赖图里自然不会有。
4. **"骨架建好后，我可以手动加几个 Player Fantasy 节再跑 §4"**。别。骨架只包含档位要求的节，§4 只会遍历骨架里**实际存在**的节。手动加的节不会被处理，反而会让 `gdd-structure-check.sh` 误报"多了一节不必要的"。
5. **"在同一个会话里先写再评审应该没问题吧"**。绝对不行。技能**明令禁止**内联提供 `/design-review`——评审者继承了作者的辩护词，独立性破坏。新会话是硬要求，不是建议。
6. **"哈希回执就是为了复用判决省时间"**。不止。它还让新会话里的评审者**知道自己该审什么**——如果指纹全匹配，它就知道"这版和上次一样，可以直接用旧结论"；如果目标文档 CHANGED 但注册表 UNCHANGED，它就知道"只需要核对文档值有没有违反注册表共识"。指纹是**盲审者的眼睛**。
7. **"TD-SYSTEM-BOUNDARY 的 REJECT 意味着流程卡死了"**。恰恰相反——它在最"便宜"的时机卡住。REJECT 的意思是"先把系统边界调对了再写 GDD"，这是一分钟的事；如果没门禁、30 份 GDD 写完才发现边界错了，返工是天级的。CONCERNS 才是"记下来继续走"。
8. **"新会话跑评审就等于重新开始，之前的评审白跑了"**。不是。哈希回执让它能复用旧判决——**内容没变就直接用，变了才重新审**。这就是指纹把"独立性"和"可复用性"同时实现的方式。

## 10. 小测验（答案都在上文）

**Q1**：为什么隐式推断要分成 6 组映射表（Inventory→5个、Combat→7个……），而不是"让 AI 自由发挥、自己想隐含系统"？

> 答案：三个理由——① 固定映射表让推断**可预测、可评审**，你能对照"背包应该隐含物品数据库、装备槽、重量规则、UI、序列化"来检查 AI 漏了什么；② 映射表**强制覆盖 UI 和序列化两类隐形刚需**，自由发挥容易漏；③ 映射表让推断逻辑**可解释**——AI 必须在对话里说"背包需要物品数据库，因为没有它背包里能放什么就没法约束"，你能判断它推得对不对。

**Q2**：假设 TD-SYSTEM-BOUNDARY 报 REJECT："装备逻辑错挂在战斗系统下了，应该独立成装备系统"。改 systems-index.md 和改战斗+装备两份 GDD，分别要花多少工作量？

> 答案：改 systems-index.md——把装备从战斗的子项改成独立系统、依赖图加一条"战斗依赖装备"、设计顺序里装备调到战斗之前，**5 分钟**。改 GDD——战斗 GDD 里所有涉及装备的章节（伤害计算、命中判定、状态效果）都要改引用方式，从"战斗自己管理装备"变成"战斗向装备系统查询"；装备 GDD 从零开始写 8 节；兄弟 GDD（背包、UI）也要改接口调用方式，**几小时甚至几天**。这就是 shift-left 的具体体现。

**Q3**：在新会话里跑 `/design-review`，哈希验章报告 combat.md 是 CHANGED、entities.yaml 是 UNCHANGED、review-receipts.sh 脚本本身是 UNCHANGED。评审者应该怎么走？

> 答案：走 Phase 1 的完整评审分支——目标文档 CHANGED 意味着"这份文档被改过、上次评审的结论不再适用"。但注册表 UNCHANGED 意味着"跨系统共识没变"——评审者不需要重新核对注册表里的值，只需要**全量重读 combat.md**，用**新会话上下文**（没有作者的辩护词、只有 GDD 本体+注册表+CLAUDE.md）做独立判断。**不能**只审"变了的章节"。
