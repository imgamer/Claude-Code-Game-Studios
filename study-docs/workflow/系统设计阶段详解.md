# 系统设计阶段（Phase 2）逐步详解 —— 从"一个想法"到"一摞可以照着写代码的 GDD"

> **一句话总览**：系统设计阶段干的事是**把整个游戏拆成一个个系统，排出设计顺序，然后一个系统一个系统写出 8 节的 GDD（游戏设计文档）**。它由两个技能接力完成：`/map-systems` 画"城市规划总图"（systems-index.md），`/design-system` 给每个系统出"施工图"（单个 GDD）；中间穿插三个总监门禁把关，最后由 `/design-review` 和 `/gate-check technical-setup` 验收放行。

依据 [map-systems/SKILL.md](file:///workspace/.claude/skills/map-systems/SKILL.md)、[design-system/SKILL.md](file:///workspace/.claude/skills/design-system/SKILL.md)、[director-gates/td-system-boundary.md](file:///workspace/.claude/docs/director-gates/td-system-boundary.md)、[director-gates/pr-scope.md](file:///workspace/.claude/docs/director-gates/pr-scope.md)、[director-gates/cd-systems.md](file:///workspace/.claude/docs/director-gates/cd-systems.md)、[gate-check/references/gate-technical-setup.md](file:///workspace/.claude/skills/gate-check/references/gate-technical-setup.md) 整理。

## 1. 初中生版：城市总规划 + 逐栋施工图

想象你要建一座新城市：

1. **先画总规划**（`/map-systems`）：这座城市需要住宅区、商业区、电厂、水厂、道路……先列出**所有功能区**（枚举），画出**谁依赖谁**（电厂不建好，住宅区通了电也没用），再决定**先建哪个**（优先级）。
2. **请专家审总规划**：建筑专家看结构合不合理（有没有把路修成死循环），预算专家看工期靠不靠谱，市长的文艺顾问看"这还是我们要的那座城市吗"。
3. **一栋楼一栋楼出施工图**（`/design-system`）：每栋楼的图纸都按**固定 8 个章节**写，每写完一节就归档一节，专家只管自己那栋楼的领域。
4. **每栋图单独会审**（`/design-review`），全部 MVP 楼栋图纸齐了才允许**开工挖地基**（进入 Phase 3 技术搭建）。

这个类比对上真实流程：功能区=系统、总规划=systems-index.md、施工图=GDD、专家会审=总监门禁、开工许可=gate-check。

## 3. `/map-systems` 逐步详解（画总图）

### 第 0 步：加载即解析配置（技术细节）

技能文件第 10 行有一条以 `!` 开头的命令：

```markdown
!`bash "${CLAUDE_SKILL_DIR}/../../hooks/yaml-helper.sh" resolve_config --keys review_mode,automation,workflow,docs.density,project.stage`
```

**技术细节**：Claude Code 在技能加载瞬间就执行这行 shell，把输出直接替换进上下文——所以技能正文开始之前，"评审模式、自动化档位、流程档位、文档深度、当前阶段"五个值已经摆在面前，不用模型中途去猜。**为什么要这样**：73 个技能如果各自在正文里写"读这个文件，没有就用某默认值"，行为会漂移；统一由脚本解析（解析链见[配置体系与rigor心智模型](file:///workspace/study-docs/workflow/配置体系与rigor心智模型.md)）保证所有技能拿到同一份答案。

### 第 1 步：读概念文档（必需上下文）

读 `design/gdd/game-concept.md`（minimal 档改读 `design/game-brief.md`）；**两个都没有就报错停止**："No game concept found. Run `/brainstorm` first."

**为什么宁可报错也不继续**：拆系统的原材料就是概念文档。没有原材料硬拆，产出的是编造的系统列表，比不产出更糟（用户会照着错误的清单往下走）。这和 [`/design-review` 拒绝评审不存在的 GDD](file:///workspace/study-docs/workflow/回填与哈希重跑机制.md) 是同一个原则：**输入不完整时，响亮地失败**。

顺带的两个技术细节：
- **按节读**：先用 Grep 找 `^#` 标题定位，再用 offset/limit 只读需要的段落——概念文档可能很长，全文读浪费上下文；
- **索引已存在则续作**：读到 systems-index.md 就展示当前状态并问"更新/设计下一个/调优先级"，**绝不推倒重建**——这是回填思想在总图上的体现。

### 第 2 步：系统枚举（这个技能的创意核心）

分两小步：

**2a. 提取显式系统**——扫概念文档四个位置：Core Mechanics（最直接）、Core Loop（暗示驱动每层循环的系统）、Technical Considerations（联机、程序化生成等）、MVP Definition（必备功能=必备系统）。

**2b. 推断隐式系统**——概念文档**从来不会**列全系统。技能内置了一组推断模式，例如：

| 你写了 | 就必然还隐含着 |
|--------|----------------|
| 背包 Inventory | 物品数据库、装备槽、重量/容量规则、背包 UI、存档序列化 |
| 战斗 Combat | 伤害计算、血量系统、命中判定、状态效果、敌人 AI、战斗 UI、死亡/重生 |
| 开放世界 | 流式加载/分块、LOD、快速旅行、地图/小地图、兴趣点追踪、世界状态持久化 |
| 联机 Multiplayer | 网络层、大厅/匹配、状态同步、反作弊、网络 UI |

**为什么要显式做这一步**：漏掉的系统会在后面以"惊吓"的形式出现——写到一半发现存档系统没人设计。**把隐含系统在纸面上显式化，就是把未来的惊吓变成现在的清单**。同时技能要求"在对话里解释每个隐式系统为什么需要"——不是甩给你一张表，而是让你能判断它推得对不对。

**2c. 用户评审**：按类别展示清单（每个系统：名字/类别/一句话描述/显式还是推断），然后问三个问题：有漏的吗？该合并/拆分吗？有这游戏不需要的吗？——三档 automation 的行为差异在这里显现：collaborative 反复问到达成一致；guided 只问一次；autonomous 不问，用 `log_decision` 记录后继续。

### 第 3 步：依赖映射 + 第一个总监门禁

**3a. 判定"依赖"**：A 依赖 B = A 离了 B 就无法运转。三类启发式：
- **输入/输出依赖**：A 产出 B 需要的数据（战斗产出掉落 → 背包依赖战斗的数据结构）；
- **结构依赖**：A 提供了 B 插进去的框架（事件总线先于一切用它通信的系统）；
- **UI 依赖**：每个玩法系统都拖着对应的 UI 系统——**但 UI 排在玩法后面设计**。

**3b. 分五层排序**：Foundation（零依赖，最先）→ Core → Feature → Presentation（UI）→ Polish（教程、埋点、无障碍）。

**3c. 循环依赖检测**：A 依赖 B、B 又依赖 A 就是死结。技能给出三种解法：接口抽象（把共享部分抽成第三个系统）、同步设计、定义两系统间的合同后各自独立。**为什么要专门检测**：循环依赖拖到写代码时才暴露，代价是架构级返工；在总图阶段发现，改一行表格就行。

**3d. 展示 + 高亮风险**：瓶颈系统（很多人依赖它=高风险单点）、叶子系统（没人依赖它=可以晚设计）。

**3e. TD-SYSTEM-BOUNDARY 门禁**（`full` 评审模式才跑；solo/lean 跳过并注明）：

```
主会话 --Agent 工具--> technical-director 智能体
   传递：依赖图、分层、瓶颈、循环依赖及拟议解法
   门禁文件 td-system-boundary.md 由【智能体自己读】，主会话不读
   判决：APPROVE（边界干净，去写 GDD）/ CONCERNS（记入索引继续）
        / REJECT（结构必须先重构）
```

**技术细节——为什么门禁文件由被召唤的智能体读，而不是主会话读了转述**：主会话读了再总结，总结会丢失细节且占用主会话上下文；让智能体自己读原文件，主会话只传"文件路径 + 数据"。这是这个项目的上下文经济学：**能外包给子智能体的读取，就不留在主会话**。

**为什么这个门禁放在写 GDD 之前**：门禁原话——"在团队对它投入 GDD 写作之前，验证系统结构在架构上是健康的"。检查四个问题：边界是否清晰（每个系统管一件独立的事）、有没有 God Object（一个系统管太多）、依赖顺序会不会造成实现排期问题、Foundation 层有没有反向依赖 Feature 层。**在表格上改边界是分钟级，在三十份 GDD 上改边界是天级**。

### 第 4 步：优先级分配 + 第二个总监门禁

**4a. 自动分四个里程碑档**：MVP（概念文档"必备"区 + 它们的 Foundation 依赖）→ Vertical Slice（一个区域的完整体验）→ Alpha（其余玩法系统）→ Full Vision（润色、元系统）。

**4b. 理由表述规则**（一个很值得学的细节）：技能明文规定，解释"为什么这个系统在 MVP"时**纯技术理由不够**——"伤害系统需要伤害数学"不算合格的解释；必须同时讲玩家体验并援引设计支柱（pillar），例如"没有它玩家的核心选择就没有后果（Pillar 2：选择有重量）"。**为什么要管 AI 怎么说话**：理由是说给用户听的决策依据。用户只能判断"体验理由"是否符合他的愿景，"技术理由"他没法反驳也没法确认。还有一条防抄警告：括号里的示例槽位要用**本项目**的支柱名填——从别的游戏的示例里抄来的理由带着别的游戏的词汇。

**4c. PR-SCOPE 门禁**（`full` 模式）：召唤 `producer` 智能体，传递完整愿景范围、MVP 定义、各档系统数量×复杂度、时间线、团队规模。判决三档：REALISTIC / OPTIMISTIC（给出调整建议，问你是否应用）/ UNREALISTIC（建议先改优先级再写索引）。**为什么在写索引前做范围现实性检查**：索引一旦写好就成了后续所有排期（epic、sprint、故事）的依据；一个乐观的索引会污染整条下游。

**4d. 设计顺序**：依赖层 × 里程碑交叉排序——MVP 的 Foundation 最先，然后 MVP 的 Core……这就是"GDD 该按什么顺序写"的最终答案。

### 第 5 步：写索引 + 第三个总监门禁

**5a. 按模板填充**：[systems-index.md 模板](file:///workspace/.claude/docs/templates/systems-index.md)是一个**固定列表格**：`# / Name / Category / Priority / Status / Design Doc / Depends On`。

**技术细节——为什么是固定列契约**：技能里专门警告"不要加描述列"（Do not add a column）。原因有两层：
1. 下游消费者（`/design-system` §6、`/create-epics`）是**按列名**写的；
2. 两个脚本（`gdd-structure-check.sh`、`review-scope.sh`）按**文件名**匹配、完全不解析列——所以真正绝不能改名的列是 **`Category`**（它决定专家路由，见 design-system §6）。

那 prose 写哪？`balanced`/`thorough` 档的描述写进 `## Overview` 段落——**加列是改 schema，加段落不是**。

**5b. 写批准 + CD-SYSTEMS 门禁**：collaborative 模式必须问"我可以写入 systems-index.md 吗"；写完后（`full` 模式）召唤 `creative-director` 跑 CD-SYSTEMS 门禁，问四个愿景问题：MVP 系统集合体能不能交付核心幻想？有没有不服务任何支柱的系统（=范围蔓延嫌疑）？有没有支柱关键体验没有系统承接？核心循环缺系统吗？判决 REJECT 则必须先修订系统集；CONCERNS 可以选择"接受并记录"——以引用块 `> **Creative Director Note**` 写在 Priority Tiers 表格正下方（模板没有"每档一节"的结构，所以技能连"写在哪一节顶部"这种指示都精确纠正过）。

**5c. 更新会话状态**：写 `production/session-state/active.md`（任务/状态/文件/下一步四行）。**为什么**：这是断点续作的锚——会话断了、压缩了、换新会话了，下一个技能从这四行知道"索引已建好，该设计单个 GDD 了"。

### 第 6 步：交接给 /design-system（职责边界）

选系统（指定名字 / `next` 自动挑设计顺序里第一个未设计的 / 问用户），然后整只移交给 `/design-system`。技能里有一句明确的职责声明：

> **Do not duplicate the /design-system workflow here.** This skill owns the systems *index*; `/design-system` owns individual system *GDDs*.

**为什么要划这条线**：map-systems 知道"哪些系统待设计"，design-system 知道"怎么把一个系统写成 8 节 GDD"。如果 map-systems 也内嵌一套写 GDD 的逻辑，两处逻辑会漂移、修 bug 要修两遍。**一个技能管一件事，交接靠调用**——和智能体的 Delegation Map 是同一个思想。

### 第 7 步：建议下一步（包括出阶段门禁）

索引写完后给四个选项：开始设计第一个 GDD / 跑 `/gate-check systems-design`（进阶段门禁）/ 跑 `/gate-check technical-setup`（**出**阶段门禁，MVP 系统 GDD 齐了才有意义）/ 收工。

技能还特别注明：CD-SYSTEMS 和 TD-SYSTEM-BOUNDARY 是**本技能自带的门禁**，在这里跑，不在 `/gate-check` 里跑——`/gate-check` 只查产物存在性和阶段门禁。**两层门禁分工**：技能内门禁管"中间产物质量"，阶段门禁管"能不能进入下一阶段"。

## 4. `/design-system` 逐步详解（出施工图）

主文件只有 150 行，五个执行阶段的细节全部在 `references/1~5` 五个分文件里，主文件指示"到哪步读哪个文件，会话压缩过就重读"。**为什么拆成 references**：技能全文很长，一次全读进上下文浪费；按阶段懒加载，每个阶段只带自己需要的指令。

### §1 参数解析（references/1-parse-arguments.md）

解析 `<系统名>` 和 `--review` 覆盖；**retrofit 检测**：目标 GDD 已存在就进入回填模式——盘占位符、列清单、"绝不覆盖已有内容"（细节见[回填与哈希重跑机制](file:///workspace/study-docs/workflow/回填与哈希重跑机制.md)）。还要做**系统名→GDD 文件名转换**（系统名空格转连字符），并对照 systems-index 确认这个系统真实存在——**不存在的系统不写**，防止总图和施工图脱节。

### §2 收集上下文（references/2-gather-context.md）

读四类东西，顺序有讲究：
1. **概念文档**——这个系统服务什么支柱、在核心循环的哪一环；
2. **systems-index.md**——本系统的 Category（决定专家路由）、依赖谁、谁依赖它；
3. **依赖系统的 GDD**——"依赖"在这里兑现为约束：背包 GDD 必须遵守战斗 GDD 定下的掉落数据结构。**先读依赖再动笔，就是"防止矛盾"的第一道防线**；
4. **注册表**（技术细节）：跑 `registry.sh slice design/gdd/[本系统].md`，一次性捞出所有"source 或 referenced_by 指向本系统"的已登记事实——**这些是跨系统共识，写作时必须遵守而非重新发明**（注册表机制见[注册表机制详解](file:///workspace/study-docs/workflow/注册表机制详解.md)）。

### §3 建骨架（references/3-file-skeleton.md）

**先获得批准**（"May I create the skeleton?"），然后立即创建**完整 8 节骨架**：Overview / Player Fantasy / Detailed Rules / Formulas / Edge Cases / Dependencies / Tuning Knobs / Acceptance Criteria（另有 Game Feel 节），空节一律填占位符 `[To be designed]`。

**为什么先建空骨架而不是写完再一次性写入**：三个理由——
1. **断点锚**：文件存在了，恢复逻辑才有依据（§7：有真内容的节=完成，`[To be designed]`=待做）；
2. **消费方可探测**：`gdd-structure-check.sh` 能立刻检查 8 节是否齐全，`review-scope.sh` 能统计进度——空骨架也是"进度=0%"的有效信号；
3. **用户可见全景**：你先看到 8 个章节标题，对"这个 GDD 会包含什么"有预期，逐节填充时不会迷失。

### §4 逐节设计（references/4-section-design.md）——本阶段的心脏

每一节都走同一个循环（collaborative 模式）：

```
① 讲解：这一节要求写什么、为什么需要它（Explain）
② 提问+选项：AskUserQuestion 给出设计问题与 2-4 个方案（Options）
   └─ 复杂节先召唤专家智能体（§6 路由表），把专家分析并入选项
③ 起草：按用户决定起草这一节内容（Draft）
④ 批准：展示草稿，问"写入吗？"（Approval）
⑤ 写入：Edit 只填这一节，其他节不碰（增量写入）
⑥ 状态：更新 active.md（当前系统、完成到第几节）
```

**技术细节三条**：
- **专家只出意见不碰文件**：`When delegating via the Agent tool` 一节写明"Agents do NOT write to files directly — the main session owns all file writes"。专家的分析返回主会话→经 AskUserQuestion 呈给用户→用户拍板→主会话落笔。**写权限集中在一个地方，责任链才清楚**；
- **路由两步走**：先从索引取 `Category`（9 类），再在 13 行路由表里按"这个系统实际干什么"挑行——战斗和寻路都属 Gameplay，但专家完全不同（combat→game-designer，pathfinding→game-designer+ai-programmer）。**为什么不让一个"设计专家"包打天下**：寻路的可行性判断需要 ai-programmer 的实现经验，战斗的手感需要 art-director 的打击反馈方向——领域错了，建议就漂；
- **docs.density 控制每节深度**：terse=决策要点，balanced=要点+理由段，thorough=完整论证含备选方案取舍。节的数量由 workflow 档位定，深度由 density 定（详见[配置体系与rigor心智模型](file:///workspace/study-docs/workflow/配置体系与rigor心智模型.md)）。

**三节特别值得注意**：
- **Formulas 节**：写公式必须给具名变量和输出范围——写完会登记进 `entities.yaml` 的 formulas 分区，成为跨系统共识；
- **Edge Cases 节**：`workflow_overrides.edge_cases` 可以在**任何档位**强制要求它——边缘情况是最常被跳过又最常出 bug 的部分；
- **每节都要交叉引用**：写入前对照已批准 GDD 和注册表，发现矛盾必须亮出来（"Never contradict an existing approved GDD without flagging the conflict"），不许静默不一致。

### §5 后置验证（references/5-post-design.md）

GDD 8 节写完后的收尾四件事：
1. **结构自检**：跑 `gdd-structure-check.sh`，确认 8 节真实存在（不是占位符）、格式合规；
2. **登记注册表**：本系统新增的跨系统事实（实体/物品/公式/常量）写入 `design/registry/entities.yaml`，`source` 指向本 GDD；然后跑 `registry.sh validate` 查重名/坏路径/坏布局；
3. **更新总图**：systems-index 里本系统状态从 Not Started 改为 Designed，Design Doc 列填上文件路径；
4. **§5c 交接**——注意一个反直觉的设计：这里**禁止**问"要跑 /design-review 吗？"（"§5c forbids offering `/design-review` inline"），只呈现"下一步是新会话跑评审"的指引。

**为什么禁止内联评审**：评审智能体如果在本会话里跑，会**继承设计过程的全部历史**——它刚看着这 8 节诞生，天然倾向于给面子、放过弱点。`/design-review` 必须在**新会话**跑，让评审者只面对文件、不面对作者的辩护。这是"作者不能自审"在 AI 工作流里的落地：**用会话隔离制造评审独立性**，配合哈希回执保证"评审的就是你这版文件"。

### §7 断点恢复（Recovery & Resume）

会话中断后的恢复三步：读 active.md（进行到哪个系统）→ 读 GDD 本体按节判断完成度 → 从下一未完成节继续，已完成的节不重谈。**这是整个"增量写入"策略的红利**：每节批准即落盘，任何中断最多损失"正在讨论的那一节"，而不是整个 GDD。

## 5. 阶段出口：两道验收

单个 GDD 完成后的即时验收——**新会话**跑 `/design-review design/gdd/[系统].md`：先验哈希回执（评的是不是眼前这版），再按 8 节质量标准 + 跨文档一致性评审，判决 APPROVE / CONCERNS / REJECT（机制详见[回填与哈希重跑机制](file:///workspace/study-docs/workflow/回填与哈希重跑机制.md)）。

全部 MVP 系统的 GDD 完成、评审通过、注册表一致（`/consistency-check` 无未解决 CONFLICT）之后，跑 `/gate-check technical-setup` 出阶段。它的检查清单包括（[gate-technical-setup.md](file:///workspace/.claude/skills/gate-check/references/gate-technical-setup.md)）：

- 所有 MVP 系统有 GDD 且无 `[To be designed]` 占位符；
- **没有过期的 GDD 引用**——老 GDD 已回填后设计系统定下的决策（这一条把"设计会倒着影响先设计"制度化）；
- 注册表与各 GDD 一致；
- 总监评审（`full` 模式）无未处理 REJECT。

PASS 才进入 Phase 3 Technical Setup（引擎配置、ADR、control-manifest）。

## 6. 设计思路提炼（为什么这么做）

| 设计选择 | 直接原因 | 深层原理 |
|----------|----------|----------|
| 先总图后施工图（两个技能接力） | 单个巨型技能既管总又管细节会失控 | **关注点分离**：索引技能和 GDD 技能各管一层，交接靠显式调用 |
| 枚举时显式区分"显式/隐式"系统 | 概念文档必然漏系统 | **把未来的惊吓变成现在的清单**——纸面上补漏成本≈0 |
| 依赖分五层 + 循环检测 | 依赖关系决定实现顺序 | **拓扑排序**思想： Foundation 先行，循环是架构级死结要提前解 |
| 三个总监门禁嵌在流程中间而不是最后 | 最后才发现结构问题=全部返工 | **缺陷发现越早代价越小**（shift-left）；架构/愿景/范围三个视角**正交**，缺一不可 |
| 门禁文件由被召唤的智能体自己读 | 主会话转述有损且耗上下文 | **上下文经济学**：能外包的读取不占主会话 |
| 8 节固定骨架 + 占位符 | 消费方可探测、可恢复 | **增量写入=抗中断**；空骨架也是有效进度信号 |
| 逐节"讲解→选项→批准→落盘" | 防止 AI 一次性生成整份文档让用户追认 | **人在环中**：每个设计决定由用户拍板，AI 只提议 |
| 专家智能体只出意见不写文件 | 写权限分散则责任链断裂 | **单一写者**：主会话拥有所有文件写入 |
| 禁止内联 /design-review | 评审者不能继承作者的历史 | **会话隔离=评审独立性**，作者不能自审 |
| 固定列表格、Category 列不可改名 | 下游技能按列名消费 | **Schema 契约**：数据结构变更=所有消费者同步变更 |
| 结尾登记注册表 + 更新总图 | 单个 GDD 的产出要进入全局共识 | **局部产出必须汇入单一事实源**，否则又变影子副本 |

## 8. 常见误区

1. **"系统设计=写代码架构"**。不是。本阶段产出的是**设计文档**（系统是什么、规则是什么、公式是什么），技术架构是 Phase 3 的事。GDD 里唯一的技术内容是 Dependencies（依赖什么系统）和可行性约束。
2. **"minimal 档也要跑完整 map-systems"**。不需要——minimal 档整个阶段被一页 game-brief 取代，brief 的 build order 就是计划。强行跑全套是浪费。
3. **"枚举出的系统列表是权威，照着做就行"**。列表要过用户评审——隐式系统是 AI 推断的，可能推断过度（给小型解谜游戏推"反作弊系统"）。三个评审问题（漏？合并/拆？不需要？）就是纠偏入口。
4. **"门禁判决 REJECT = 流程卡死"**。REJECT 的意思是"先修结构再写 GDD"，恰恰是最便宜的失败时机。CONCERNS 才是"记下来继续走"。
5. **"专家智能体会把 GDD 写好"**。不会。专家只返回分析和提案，写入永远由主会话在用户批准后执行。**没有任何智能体绕过批准直接改你的文件**。
6. **"GDD 一次写完再给用户看"**。这是协作模式明令禁止的（"Never auto-generate the full GDD and present it as a fait accompli"）。逐节批准既是控制权设计，也是断点恢复的基础。
7. **"design-review 可以顺手在同一个会话里跑"**。技能明确禁止内联提供。新会话 + 哈希验章是评审独立性的两根支柱。
8. **"Formulas 节写完就完事了"**。跨系统公式/数值必须登记进 entities.yaml 并跑 validate——不登记的公式在下一个系统的 GDD 里就会被重新发明一遍。

## 9. 小测验（答案都在上文）

**Q1**：为什么 TD-SYSTEM-BOUNDARY 门禁安排在"依赖映射之后、写任何 GDD 之前"，而不是全部写完再统一审？

> 答案：门禁验的是"系统边界在架构上是否健康"。边界错了，每一份基于错误边界写的 GDD 都要返工——先写后审的返工量是 30 份 GDD，先审后写是改一行表格。缺陷发现越早，修复代价越小（shift-left 原理）。

**Q2**：`/design-system` 的专家路由为什么要"先取 Category、再按系统实际干什么挑行"两步走？

> 答案：9 个 Category 是粗分类（Gameplay 同时涵盖战斗和寻路），13 行路由表是细分。两步走保证"每类都有兜底行、每行都是对的专家"——战斗的打击反馈要 art-director，寻路的可行性要 ai-programmer，领域错了建议就漂。

**Q3**：为什么 `§5` 结束时禁止直接问"要跑 /design-review 吗？"，而 systems-index 写完后可以问 CD-SYSTEMS 门禁？

> 答案：CD-SYSTEMS 是`full` 模式下由本技能召唤的独立智能体，且门禁定义文件由智能体自己读——它没有继承设计历史。而内联跑 /design-review 会让评审者带着"刚写完这份文档的记忆"评审，独立性被破坏。所以设计评审必须新会话跑，技能只能指引、不能代跑。
