# 概念阶段（Phase 1）逐步详解 —— 从"我想做个游戏"到"一整套可以开工的规格"

> **一句话总览**：Phase 1 干的事是**把"一个想法"变成"一整套规格"**。它分两条路——`workflow: minimal`（默认）走 Lean Brief 一页纸，`standard/full` 走完整 8 阶段 brainstorm + 四个总监门禁 + 引擎配置 + 美术圣经 + `/map-systems` 总图。**Phase 1 完成的标志**不是写完 game-concept.md，而是 systems-index.md 也写好了——它是 Phase 1 的最后一步，Phase 2 的入口。

## 0. Phase 1 全景图（先搞清楚哪些属于这个阶段）

### 0.1 workflow-catalog 定义的 Phase 1 步骤

```yaml
concept:               # Phase 1
  steps:
    - brainstorm        # 发现游戏概念（minimal=一页 brief；standard/full=game-concept.md）
    - engine-setup      # 引擎版本 + 技术栈 + project.yaml 配置
    - game-concept      # （和 brainstorm 是同一个产出，minimal 档不存在）
    - design-review-concept  # 概念评审（非必需但推荐）
    - art-bible         # 美术圣经（full 档必需，standard 档有视觉资产故事时必需）
    - map-systems       # 拆系统、画依赖图、排优先级 → systems-index.md
  next_phase: systems-design  # Phase 2 的入口
```

**关键认识**：Phase 1 的边界是**"产出 systems-index.md"**——它既是 Phase 1 的最后一步，也是 Phase 2（写单个 GDD）的入口。所以 `/map-systems` 的依赖映射、TD-SYSTEM-BOUNDARY 门禁虽然和"概念"关系不大，**但它属于 Phase 1**。

### 0.2 两条路径：minimal vs standard/full

| 维度 | minimal（默认） | standard / full |
|------|----------------|----------------|
| 设计产出 | 一页 `design/game-brief.md` | 完整 8 节 `design/gdd/game-concept.md` + Pillars + Art Bible + Systems Index |
| brainstorm 阶段数 | 4 步 Lean Brief | 8 阶段完整概念流程 |
| 总监门禁 | **没有**（跳过全部 4 个） | CD-PILLARS + AD-CONCEPT-VISUAL + TD-FEASIBILITY + PR-SCOPE |
| map-systems | **不是必需**（brief 的 build order 就是计划） | **必需**（systems-index 是 Phase 2 的入口） |
| 阶段门禁 | **没有**（project.stage 一直是 Concept） | concept → systems-design 有正式门禁 |
| 适合 | Game jam、小项目、设计在脑子里 | 多人团队、商业项目、学完整管线 |

**为什么要同时维护两条路径**：新用户一上来就被 full 流程吓退——15 轮对话 + 4 个总监门禁 + systems-index + 8 节 GDD 骨架，token 花掉一半还没写一行代码。minimal 档让他能在 10 分钟内产出一页 brief 然后开始写代码，项目"跑起来了"之后再升级 rigor，现有文件不会丢，`/help` 会告诉他新档位要求补什么。

### 0.3 两条路径的分叉机制深化（怎么选、怎么切、怎么升级）

#### 分叉点在哪里：技能加载瞬间的 resolve_config

brainstorm SKILL.md 第 10 行的 `!` 命令在**技能加载瞬间**就执行——它直接读 `project.yaml` 的 `modes.rigor` 或 `modes.workflow`，并输出到技能上下文。**分叉发生在 SKILL.md 正文第一行之前**——技能正文开始时，"走哪条路"已经被锁死了。

```bash
bash .claude/hooks/yaml-helper.sh resolve_config --keys review_mode,automation,docs.density,workflow
# 输出：
# workflow: minimal (rigor:minimal)        ← 从 modes.rigor 展开
# 或 workflow: standard (project.yaml)    ← project.yaml 显式设了
```

brainstorm SKILL.md 第 19-24 行有一个**显式的 if/else 分支**（技术文档里很少见这种直接的分叉语句）：

```markdown
- **`minimal`:** the Lean Brief flow below — a one-page `design/game-brief.md`,
  then stop. No discovery questions, pillars, director gates or
  `game-concept.md`, and do not load `references/full-concept.md`.
- **`standard` or `full`:** read `references/full-concept.md` and follow it.
```

关键是最后那句——**minimal 档不加载 full-concept.md**（8 阶段完整流程描述文件）。这是懒加载的极端形式：一个文件决定了另一个文件**根本不进上下文**。两个流程不能同时存在于同一个技能的执行上下文里，谁在当前档位需要谁进来。

#### 路径切换：改 rigor，现有文件保留

用户随时可以 `/settings modes.rigor=full` 升级档位。升级后：

1. **现有文件不删**——`design/game-brief.md` 继续存在；
2. **`/help` 会告诉你缺什么**——它重新读 workflow-catalog 的 `concept` phase steps，发现 `workflow: full` 下必需的 `game-concept.md`、`systems-index.md`、`art-bible.md` 都不存在，会列成 REQUIRED blockers；
3. **补文件不是从零开始**——`/brainstorm` 会检测到 `game-brief.md` 存在（full-concept.md 第 17 行），把它当成"粗版 concept"来续作；`/art-bible` 会检测到 game-brief 里的 working title / pitch / "Who it's for" / Art & audio direction 作为种子输入（art-bible SKILL.md 第 48-50 行）。

**降级同理**：`/settings modes.rigor=minimal` 之后，brief 变成设计产物，game-concept.md 和 systems-index.md 变成 legacy 文件（不阻塞任何流程）。`project.yaml` 里没写 `modes.rigor` 时默认 minimal——**最宽容的起点**。

#### minimal 档 MVP 硬卡 ≤7 项的实现

Lean Brief 流程里 MVP 有一个硬卡（SKILL.md 第 58-60 行）：

> **MVP:** the short list that makes it the game; each item becomes a story. **More than 7 items: push back.** Say it is too long for an MVP, propose which items to cut (the ones the core loop works without), and keep the brief to 7 or fewer.

技术细节：AI 的行为是**主动 push back**——不是"超过 7 项就报错"，而是"解释为什么太长、建议剪掉哪些"。剪掉的项自动进入 `Out of scope` 字段。为什么这么做？因为 brief 的 build order 就是 `/create-stories` 的 plan——7 项 MVP + 对应 build order = 7 个 story。超过 7 项的 MVP 实际上是"把 vision 全量堆到 MVP"，等于回到了 full 流程的 scope tiers 设计——那还不如直接用 full 档。

## 1. `/brainstorm` 技能：发现游戏概念

### 1.1 技能加载即解析配置（技术细节）

brainstorm SKILL.md 第 10 行有一条 `!` 开头的命令：

```markdown
!`bash "${CLAUDE_SKILL_DIR}/../../hooks/yaml-helper.sh" resolve_config --keys review_mode,automation,docs.density,workflow`
```

**技术细节**：Claude Code 在技能加载瞬间就执行这行 shell，把输出直接替换进上下文——所以技能正文开始之前，"评审模式、自动化档位、文档深度、流程档位"四个值已经摆在面前，不用模型中途去猜。**而且有一条路径分叉**：如果 `workflow=minimal`，技能**不加载** `references/full-concept.md`（full 档的 8 阶段流程描述），直接走 Lean Brief 流程。这就是"懒加载"——两个流程不能同时存在于上下文里，谁在当前档位需要谁进来。

### 1.2 Lean Brief（minimal 档）：4 步一页纸

brainstorm SKILL.md 第 41-82 行定义了 Lean Brief——"A few exchanges, not fifteen: capture the thinking that carries the game on one page, then get to code."

**Step 1 — 概念提案**（1 个创造性问题）：
- 用户没传提示 → 问一个开放式问题；传了提示（如 `roguelike deckbuilder`）→ 基于提示提出 2-3 个一行概念（verb-first 或 genre+mashup）；
- **只提一行**，不是完整 concept card——minimal 档不需要工作标题、电梯对话、核心幻想这些字段；
- 三个 automation 档位**都必须问**这个问题（"autonomous" 也不能跳过）——因为这是用户决定游戏方向的关键选择。

**Step 2 — 填 brief 字段**（几个字段一轮，共三轮左右）：

| 字段 | 怎么填 | 为什么这个字段在 minimal 档仍然重要 |
|------|--------|-----------------------------------|
| Working title | 从选中的概念提议一个，让用户改 | `/create-stories` 用它命名 epic 文件夹 |
| Pitch | 一句激动人心的话 | 项目的一句话描述，写代码时给你锚定 |
| Core loop | 2-4 步玩家重复做的事 | MVP 实现的核心——如果这步写得模糊，代码不知道先写什么 |
| Player goal & fail state | 玩家想做什么 + 怎么输 | `/create-stories` 把它变成 story 的验收标准 |
| MVP | **必须 ≤7 项** | 超过 7 项要"push back"——说清楚核心循环不需要哪些、建议剪掉；每一项最终变成一个 story |
| Out of scope | 特意不做的 | 被剪掉的项放这里，记录"我们决定不做什么"以防范围蔓延 |
| Build order | 风险最高/最没验证的先 | 直接替代了 full 档需要的 systems-index 设计顺序 |
| 三个 one-liner | "Who it's for / what they feel" / Art & audio direction / Reference game | 快速锚定方向，不展开 |

**Step 3 — 写 brief**（**必须显式 yes**）：
- "Brief is ready. May I write it to `design/game-brief.md`?"
- `Yes — write it` / `Revise a field first`；
- 修改时"展示 before and after 再问"；
- **绝对不能写 `design/gdd/game-concept.md`**——minimal 档的设计产物就是 brief，不是概念文档。

**Step 4 — 下一步指引**：
- 读 `project.yaml` 的 `engine.name`：**minimal 档通常 engine-setup 先跑**（workflow-catalog 里 minimal path 的第一步是 `/setup-engine`）；
- 然后 `/create-stories`（把 MVP 列表变成 stories，build order 就是计划，不经过 create-epics/sprint-plan）；
- 然后 `/dev-story`（第一行游戏代码）。

**Step 5 — 收尾**：Verdict: COMPLETE — game brief written; next stop is code.

#### Start：检测概念文档是否已存在

**技术细节**：先用 Glob 查 `design/gdd/game-concept.md` 和 `game-pillars.md` 是否存在——存在就**续作**（读各节状态，补上缺失的 Pillars 或更新 Phase 4 之后的阶段），不存在才从头开始。**按节读**：先 Grep `^#` 找标题定位，再用 offset/limit 只读需要的段落——概念文档可能几十 KB，全文读浪费上下文。

**为什么要续作**：会话可能中断、压缩、换新会话——已有文件是断点恢复的锚。如果 Pillars 已经锁定（Phase 4 做完了），续作就从 Phase 5 开始，不重谈 Pillars。

#### Phase 1：Creative Discovery（创意发现）——从"人"出发，不是从"游戏"出发

full-concept 第 19-35 行规定了一个独特的起点设计——"Start with the person, not the game"：

1. **开放性问题**（plain text，不是预设选项，让用户能输入任何游戏）：
   - "一个游戏里让你感动/激动的时刻，是什么创造了它？"
   - "一个你一直想要但从没找到过的游戏幻想？"
   - "你花时间最多的三个游戏，为什么？"
   - "你爱什么类型、避什么类型？然后：挑战、放松、故事、自我表达？"

2. **三个闭合选项问题**（**必须一起问**，因为它们共同决定 Creative Brief）：
   - 体验四选一："你最想让玩家有什么体验？"（Challenge & Mastery / Story & Discovery / Expression & Creativity / Relaxation & Flow）
   - 开发时间："你实际的开发周期？"（Weeks / Months / 1-2 years / Multi-year）
   - 开发经验："你的开发旅程在哪？"（First game / Shipped before / Professional background）

3. **汇总 Creative Brief**（3-5 句情感目标 + 品味 + 约束），回读给用户确认。

**设计思路**：这 4 个开放性问题 + 3 个闭合问题，本质上是**把用户模糊的"我想做个游戏"变成"你是什么样的人、你想给玩家什么感觉、你有什么约束"**——这比直接问"你想做什么游戏"得到的答案有质量得多。三个闭合选项必须一起问，因为它们是**协同变量**：选 "Multi-year" + "First game" 是不自洽的组合，需要在同一轮回答里暴露出来。

---

#### Phase 2：Concept Generation（概念生成）——三选（或组合）

full-concept 第 37-53 行规定：**生成三个不同方向的概念**，每个必须满足 8 个字段（Working Title / Elevator Pitch / Core Verb / Core Fantasy / Unique Hook / Primary MDA Aesthetic / Estimated Scope / Why It Could Work / Biggest Risk）。

三种生成策略**必须混用**（不能三个都用同一种）：

| 策略 | 怎么用 | 例子 |
|------|--------|------|
| **Verb-first** | 从核心动词出发（build / fight / explore / solve / survive / manage） | 从 "manage" 出发 → 管理一座城市 vs 管理一支军队 |
| **Mashup** | 类型 A + 主题 B，张力就是钩子 | "farming sim + cosmic horror"（种田同时对抗宇宙恐怖） |
| **MDA backward** | 从美学目标倒推机制 | 先定 "Fellowship + Exploration" → 什么样的机制让玩家觉得是伙伴、在探索？ |

**关键规则**（第 52 行）：三个 automation 档位**都必须问这个问题**——"Generate three distinct concepts... then ask one question with these five options: Concept 1 / Concept 2 / Concept 3 / Combine / Generate fresh"。**AI 不能替用户选方向**，哪怕是 autonomous 模式也必须用 `log_decision` 记录"用户选了什么"，不能自己拍板。

**为什么这很重要**：游戏方向是**用户的核心创意决策**——AI 可以帮他发散（三个概念）、帮他权衡（每个给风险评估），但**不能替他拍板**。autonomous 模式下 AI 能替用户拍技术决策（如"我帮你选 Godot"），但不能替他拍"我想做什么游戏"这个创意决策。

#### Phase 3：Core Loop（核心循环）——四层循环 + 自我决定论

full-concept 第 55-68 行：对选中的概念，先问 2 个具体问题（核心动作的 feel、最重要的设计变量），然后依次描述四层循环 + 自我决定论动机分析。

**四层循环模型**（值得记住，因为它贯穿游戏设计全流程）：

| 循环 | 时长 | 回答什么问题 | 例子（战斗 Roguelike） |
|------|------|-------------|----------------------|
| **30-second loop** | 10-30 秒 | 核心动作本身爽吗？反馈、时机、深度是什么？ | 挥刀砍怪——命中有粒子特效+震屏，0.3 秒冷却，有暴击判定 |
| **5-minute loop** | 3-10 分钟 | 瞬间怎么变成循环？"再来一局"的起点在哪？做什么选择？ | 跑一层地牢，收集掉落，选择继续下一层还是回村庄 |
| **Session loop** | 30-120 分钟 | 一次完整的游玩会话，停在哪？会话间的钩子是什么？ | 玩一局到死亡，选择是"立刻再来一局"还是"看一眼排行榜" |
| **Progression loop** | 数小时到永远 | 玩家怎么成长？长期目标是什么？什么时候算通关？ | 每局通关解锁新角色/新武器，长期目标是击败最终 Boss |

**自我决定论（SDT）动机检查**（三个心理需求）：

| 需求 | 在游戏里意味着什么 | 如何体现 |
|------|------------------|---------|
| **Autonomy（自主）** | 玩家感觉自己有选择、自己的决定重要 | 多种构建路线、技能树分支、可跳过的内容 |
| **Competence（胜任）** | 玩家能感到自己在进步、在掌握 | 清晰的反馈、渐进难度、可度量的成长 |
| **Relatedness（关联）** | 玩家感到自己和其他玩家/NPC有连接 | 合作模式、社交系统、有记忆的 NPC |

**设计思路**：四层循环回答"玩家玩的时候到底在做什么"——30 秒的循环如果不满足，整个游戏就没爽点；SDT 回答"玩家为什么还想玩"——没有哪个心理需求被满足，玩家会玩一次就走。这两个框架是从"体验"出发倒推"机制"的工具，MDA 框架的直接应用。

#### Phase 4：Pillars + 四个总监门禁（本阶段最复杂）

full-concept 第 69-106 行是 brainstorm 的核心关卡——Pillars（支柱）和四个门禁。

##### Pillars 机制详解

**什么是 Pillar**（设计支柱）：3-5 个，每个有**名字 + 一句话定义 + 设计测试**（"当我们在 X 和 Y 之间辩论时，这根支柱选 __"）。设计测试是关键——没有它，支柱就是空的口号。例子：

> Pillar 2 — **敏捷而非力量**：玩家通过灵活移动和时机掌握而非堆攻击力解决问题。设计测试：当新敌人既能被"快速闪避"击败又能被"升级攻击力"碾压时，选前者。

**反支柱（Anti-pillars）**：3 或更多，"我们**不会**做 [X]，因为它会破坏 [Pillar Y]"。反支柱的作用是**显式划定范围**——让设计决策时知道"哪些是我们故意不做的"，防止范围蔓延。

**支柱之间要有张力**（"pull against each other a little"）——如果所有支柱都朝同一个方向，就等于只有一根支柱；如果完全矛盾，就等于没有支柱。理想状态是"它们指向不同的方向，但都服务于同一个核心幻想"。

##### CD-PILLARS 门禁（Creative Director — Pillar Stress Test）

[cd-pillars.md](file:///workspace/.claude/docs/director-gates/cd-pillars.md) 的 Prompt 原文：

> "Review these game pillars. Are they falsifiable — could a real design decision actually fail this pillar? Do they create meaningful tension with each other? Do they differentiate this game from its closest comparables? Would they help resolve a design disagreement in practice, or are they too vague to be useful?"

**四个具体检查**（每个都对应一个支柱可能失败的方式）：

| 检查 | 检测什么 | 支柱失败的表现 |
|------|----------|---------------|
| 可证伪 | 真实设计决策能不能真的失败这根支柱 | "我们做敏捷游戏"→ 有一个敌人设计成"必须堆攻击"，但支柱没说清这种情况算"失败"还是"例外" |
| 张力 | 支柱之间有没有有意义的张力 | 所有支柱都指向"快速、简单"→ 没有区分度 |
| 差异化 | 能不能和同类游戏区分开 | "像 Hades，但更像 Hades"→ 支柱没说清独特性 |
| 可操作性 | 能不能帮解决设计分歧 | "我们做有趣的游戏"→ 太模糊，遇到分歧时还是不知道该选什么 |

**判决**：APPROVE（支柱强）/ CONCERNS [具体建议]（需要打磨）/ REJECT（支柱太弱，不够用）。

##### AD-CONCEPT-VISUAL 门禁（Art Director — Visual Identity Anchor）

[ad-concept-visual.md](file:///workspace/.claude/docs/director-gates/ad-concept-visual.md) 和 CD-PILLARS **并行**跑（full-concept 第 89 行："Hand them out together where you can"）。Prompt 要求艺术总监给 2-3 个视觉方向，每个方向提供：

1. **一行视觉规则**（"everything must move" / "beauty is in the decay"）——所有视觉决策都要能指向这行；
2. Mood + 氛围目标；
3. Shape language（sharp / rounded / organic / geometric）；
4. Color philosophy（调色板方向、颜色在这个世界里的含义）。

**判决**（和其他门禁不同）：CONCEPTS（多个方向可供选择）/ STRONG（一个方向明显更优）/ CONCERNS（支柱没给出足够的视觉方向，列出哪个支柱没提供方向）。

**为什么判决类型不同**：CD-PILLARS 是"判断支柱好不好"（只有好/需打磨/不行），而 AD-CONCEPT-VISUAL 是"给选择"（"给你 3 个方向，选哪个都行"或"有一个明显更优"或"支柱没提供足够方向所以我没方向"）。

##### 两个门禁的交互（关键机制）

full-concept 第 92-103 行精确规定了两个门禁判决后的对话流：

```
┌─ CD-PILLARS 返回 APPROVE ──────────────────────────────────────────┐
│  Pillars 问题（锁还是修订）+ Visual Anchor 问题（2-3 选 1）一起问  │
│  如果 AD 返回 STRONG → 标记推荐项；如果 CONCERNS → 展示理由并给     │
│  "修订 Pillars / 自己描述方向" 选项                                │
└────────────────────────────────────────────────────────────────────┘

┌─ CD-PILLARS 返回 CONCERNS 或 REJECT ───────────────────────────────┐
│  先单独解决 Pillars 问题；解决后再单独问 Visual Anchor 问题          │
└────────────────────────────────────────────────────────────────────┘

NOT ASSESSED（任一门禁）→ 不是批准。补缺失输入重跑，或记录为 NOT ASSESSED
```

**设计思路**：CD-PILLARS 决定"游戏的灵魂"，AD-CONCEPT-VISUAL 决定"游戏的脸"。如果灵魂还没站稳，先把灵魂搞对再选脸；灵魂站稳了，脸可以和灵魂一起讨论。NOT ASSESSED 永远不能当批准——它只意味着"缺了什么东西导致我无法判断"，不是"好的"。

**Visual Identity Anchor 的去处**：选中的方向（名称 + 一行视觉规则 + 2-3 条支持原则含设计测试 + 色彩哲学）写入 game-concept.md 的一个新 section，同时**作为 art-bible 的种子输入**。这就是"brainstorm 的 Phase 4 门禁直接喂给 Phase 1 后面的 art-bible"的跨阶段耦合——brainstorm 不只是产出一个文档，它的输出是后续多个技能的输入。

### 2.2 引导式引擎选择的决策矩阵（6 个问题的顺序有讲究）

[2-guided-mode.md](file:///workspace/.claude/skills/setup-engine/references/2-guided-mode.md) 规定了 6 个问题**必须按这个顺序问**：

| 顺序 | 问题 | 为什么这个位置 |
|------|------|---------------|
| **Q1** | Prior experience | **先问**——prior experience 是权重最高的因素，有过经验就直接推荐、跳过矩阵 |
| **Q2** | Target platform | **第二**——platform 直接排除/强烈偏好引擎（Mobile→Unity 强推、Web→Godot 干净导出） |
| Q3 | 2D / 3D / both | 补充 |
| Q4 | Primary input method | 补充 |
| Q5 | Team size | 补充 |
| Q6 | Language preference + Budget | 补充 |

**平台规则硬编码**（2-guided-mode 第 50-55 行）：
- Mobile → Unity strongly preferred；Unreal poor fit；Godot viable for simple mobile
- Console → Unity or Unreal；Godot 需要第三方 publisher 或额外工作
- Web → Godot exports cleanly；Unity WebGL functional；Unreal poor web support
- PC only → all viable
- Multiple → Unity most portable

**为什么 platform 在 experience 之后**：prior experience 是"如果我已经会用 Unity，那 Mobile 平台选 Unity 比我学 Godot 快"——experience 先答，platform 作为 modifier；但如果 experience 是 "None"，platform 就变成"哪些引擎根本不能用"的硬排除。

### 2.3 project.yaml + technical-preferences.md 双写机制

setup-engine SKILL.md 第 118-120 行：

> "project.yaml is the primary config store (v1.1). Always dual-write engine config to BOTH project.yaml (primary) and technical-preferences.md (legacy mirror). If the two ever diverge, project.yaml is authoritative."

**设计思路**：v1.1 版本把配置单一事实源从 technical-preferences.md 迁到 project.yaml，但 v1.0 的消费者（比如 `.claude/docs/technical-preferences.md` 里硬编码读引擎的旧逻辑）还在。双写保证新旧两套消费者都能读到引擎配置；同时规定"project.yaml 是权威"——如果真的分叉了（比如有人手动改了旧文件），project.yaml 说了算。

**为什么不直接删 technical-preferences.md 里的引擎配置**：因为有些钩子、规则、旧技能还在读它。渐进迁移 vs 硬切——双写是渐进迁移的典型做法。

#### 2.3a 双写的四个 blocks + Verify 步骤（具体实现）

[5.5-project-yaml.md](file:///workspace/.claude/skills/setup-engine/references/5.5-project-yaml.md) 规定了写入 project.yaml 的**四个固定 YAML block**：

```yaml
engine:          # 引擎名 + 版本 + 语言 + 渲染后端 + 物理后端
  name: "Godot"
  version: "4.7"
  language: "GDScript"
  rendering: "Forward+"         # Godot 的 rendering 取决于 platform + 2D/3D
  physics: "Jolt"               # 物理后端也取决于这些

specialists:     # 路由表：哪个文件扩展名路由到哪个专家智能体
  "*.gd": godot-gdscript-specialist
  "*.cs": godot-csharp-specialist

naming:          # 命名约定（Godot 有引擎特定的规则）
  class: PascalCase
  function: snake_case

commands:        # 构建/运行命令（引擎特定）
  run: "godot --path . --headless"
  import: "godot --headless --path . --import"
```

**两个容易漏的实现细节**：

1. **Godot 的 rendering/physics 取决于 platform + 2D/3D**（不是引擎名能单独决定的）。2D web target 用 Compatibility + Godot Physics 2D，3D non-web 用 Forward+ + Jolt。Unity/Unreal 只有一条 `any` 行，引擎名本身就够了。[5.5-project-yaml.md 第 45-57 行](file:///workspace/.claude/skills/setup-engine/references/5.5-project-yaml.md#L45-L57) 有完整的映射表。

2. **双写必须同步验证**——写完 project.yaml 之后，setup-engine 跑一个 Verify 步骤：读 technical-preferences.md 的引擎块，对照 project.yaml 检查 name/version/language 是否一致。如果不一致（应该不会发生，但万一有人手动改了其中一个），以 project.yaml 为准修正 technical-preferences.md 并报告。

**为什么 specialists 和 naming 也写入 project.yaml**：因为 routing 规则和命名约定也是"引擎相关、项目级、必须统一"的配置——它们和引擎名、版本、语言是同一类信息。把分散在多处的引擎配置集中到一个 YAML 文件，任何需要引擎信息的消费者（hooks、rules、技能）都只需要 grep 一个文件。

### 2.4 Knowledge Gap 检测 + WebSearch 补文档

LLM 的训练数据有截止日期——引擎版本 4.7 可能在训练数据之后发布。如果 setup-engine 直接用训练数据里的 API 调用方式，可能会调用**已废弃**的 API 或遗漏**新增**的 API。

[6-knowledge-gap.md](file:///workspace/.claude/skills/setup-engine/references/6-knowledge-gap.md) 的核心逻辑：
1. 拿到引擎版本号；
2. 用 WebSearch 查这个版本的发布日期、破坏性变更、废弃 API；
3. 如果**发布日期在 LLM 训练数据之后**，就标记为 Knowledge Gap；
4. 生成引擎参考文档（[7-reference-docs.md](file:///workspace/.claude/skills/setup-engine/references/7-reference-docs.md)）：VERSION.md（版本号 + 训练数据截止日期 + 是否有 gap）+ deprecated-apis.md + breaking-changes.md + migration-guide.md。

**技术细节**：这不是"为了安全起见多查一查"——而是**必须查**。因为 Claude Code 的专家智能体（godot-gdscript-specialist 等）在给建议时会读这些参考文档（setup-engine §9 的 Version Awareness section 明确要求专家读 VERSION.md），如果参考文档没更新，专家会用旧版 API 建议。

#### 2.4a Knowledge Gap 三档 + 闭环的完整实现

[6-knowledge-gap.md](file:///workspace/.claude/skills/setup-engine/references/6-knowledge-gap.md) 规定了**三档风险等级**（不是只有"有 gap / 没 gap"）：

| 风险等级 | 判定标准 | 影响 |
|----------|----------|------|
| **LOW RISK** | 版本在训练数据截止日期之后 ≤ 3 个月 | 模型可能知道大部分变更，但应该跑 WebSearch 确认 breaking changes |
| **MEDIUM RISK** | 版本在训练数据截止日期之后 3-12 个月 | 模型可能知道一些新增 API 但不知道废弃 API；必须补 deprecated-apis.md |
| **HIGH RISK** | 版本在训练数据截止日期之后 > 12 个月 | 模型几乎肯定用旧版 API；必须补 deprecated-apis.md + breaking-changes.md + migration-guide.md |

**闭环怎么连**（四个步骤，每步都是下一步的输入）：

```
§3 拿到引擎版本 + §2 用户告诉 platform + 2D/3D
    →
§6 Knowledge Gap 检测
    WebSearch 查：
      ① 版本发布日期（和训练数据截止日期对比，定风险档）
      ② 废弃 API 列表（从 release notes / 官方文档提取）
      ③ 破坏性变更列表（从 release notes 提取）
      ④ 迁移指南（如果有）
    →
§7 写引擎参考文档（docs/engine-reference/<engine>/）
    VERSION.md        → 专家读：版本号 + 训练数据截止日期 + 风险档
    deprecated-apis.md → 专家读：哪些 API 不该用了、替代是什么
    breaking-changes.md → 专家读：哪些行为变了
    migration-guide.md → 专家读：从旧版升级到这版要做什么
    →
§9 Version Awareness section 注入专家智能体文件
    强制专家每次给建议前先读 VERSION.md + deprecated-apis.md
    （如果 HIGH RISK，还要读 breaking-changes.md + migration-guide.md）
```

**风险方向的不对称设计**：LOW→MEDIUM→HIGH 的升级是**累积的**——MEDIUM 档必须做 LOW 档的所有事（WebSearch 确认）+ 补 deprecated-apis.md；HIGH 档必须做 MEDIUM 档的所有事 + 补 breaking-changes.md + migration-guide.md。**没有降级**——从 HIGH 档不能只做 LOW 档的事，风险越高必须做的越多。

**为什么 VERSION.md 独立出来**：因为它是**专家每次都必须读**的文件（Version Awareness section 第 1 条就是"Read VERSION.md"），而 deprecated-apis.md 只有当专家给某个具体 API 建议时才需要查。VERSION.md 体积小（几行）、读起来快，作为**风险意识开关**——专家读完知道"这是一个高风险版本，我得更小心"。

### 2.5 Version Awareness section 注入

setup-engine §9 要求**给每个引擎专家智能体文件加 "Version Awareness" section**（必须先问用户批准再编辑）：

```markdown
## Version Awareness

1. Read `docs/engine-reference/<engine>/VERSION.md` to know what version this project targets
2. Check deprecated APIs before suggesting code — read `docs/engine-reference/<engine>/deprecated-apis.md`
3. Check breaking changes for relevant version transitions — read `docs/engine-reference/<engine>/breaking-changes.md`
4. Use WebSearch to verify uncertain APIs — training data may not include this engine version
```

**为什么要加这个 section**：专家智能体默认"知道所有 Godot API"——但它知道的是**训练数据里的 Godot API**，不是**用户项目锁定的那个版本的 Godot API**。这个 section 强制它每次给建议前先读项目特定的参考文档，解决"模型知识 ≠ 项目知识"的问题。

### 2.6 §7.5 Scaffold（Godot 为例）

Godot 项目初始化有一步特殊操作：

```bash
godot --headless --path . --import
```

这不是简单的"创建项目文件"——Godot 的 `.godot/` 缓存、资源导入元数据（`.import/`）、scene 文件（`.tscn`）在 `godot --import` 之后才会生成。setup-engine 必须**实际运行**这个命令（需要用户电脑上装了 Godot），否则后续的 `.import/` 引用会悬空。

## 4. `/art-bible`：美术圣经（Phase 1 最后一个文档步骤）

### 4.1 9 节 + 档位要求

| workflow | 要求 |
|----------|------|
| `full` | 全部 9 节必须 |
| `standard` | 有视觉资产故事时必需，最少 4 节（1-4）；`art_bible_strict: true` 强制 9 节 |
| `minimal` | 不需要，可以自愿跑 |

**9 节清单**：
1. Visual Identity Statement
2. Visual Hierarchy & Contrast
3. Color Philosophy（从 AD-CONCEPT-VISUAL 拿到的 Visual Identity Anchor 直接喂这里）
4. Typography & Text Rendering
5. Entity Visual Guidelines（角色、敌人、NPC 的视觉锚点）
6. UI Style Guide
7. Environment & Atmosphere
8. Technical Constraints（分辨率、贴图大小、性能预算）
9. Animation & Motion

**关键耦合**：§3 Color Philosophy 的输入就是 brainstorm Phase 4 的 AD-CONCEPT-VISUAL 门禁输出——"一行视觉规则 + 2-3 条支持原则含设计测试 + 色彩哲学"。brainstorm 不只是产出 game-concept.md，它的门禁输出是 art-bible 的直接种子。

### 4.2 Retrofit 检测的"不加载完整文件"技巧

art-bible SKILL.md 第 57-74 行有一个很值得学的技术细节——检测 retrofit 时**不读取完整文件**：

```
Grep "^## " → 拿到节标题和行号 → 标题间的距离 = 节大小
Grep "\[To be designed\]" → 拿到占位符位置
```

**为什么**：art-bible 写完了可能有 30KB+，在 retrofit 模式下你要做的是"只补缺失的节"——加载完整文件就是加载了你**不会碰**的内容（已经完整的节），浪费 token。两节 Grep 足够告诉你哪个节是 Complete / Placeholder / Empty。只有当两节 Grep 的结果有歧义时（比如标题距离 500 行但中间没占位符），才 Read 那个节的行范围——**读这个节的 offset+limit，绝不读整个文件**。

这个技巧被 `/design-system` 的 retrofit 检测也用了——**同一套"先 grep 结构再按节精确读"的技术**，避免在增量更新时浪费上下文。

### 4.3 Visual Identity Anchor 的流转机制深化（brainstorm 输出 → art-bible 输入的完整链路）

Visual Identity Anchor（以下简称 VIA）是 brainstorm → art-bible → 后续美术流程之间**唯一的结构化视觉决策数据**——它不是一段散文，而是一组有固定字段的"锚定规则"。它的流转链路经过**三个技能、两个文件、零注册表中转**。

#### 第一步：brainstorm Phase 4 AD-CONCEPT-VISUAL 门禁产出 VIA

art-director 被召唤后，门禁 prompt 要求它输出 2-3 个视觉方向，每个方向的**固定字段**（full-concept.md 第 87-88 行）：

```yaml
visual_anchor:
  name: "Gritty Cartoon"          # 方向名称（简洁，能做文件名）
  one_rule: "beauty is in the decay"  # 一行视觉规则——所有决策都指向这行
  supporting_principles:           # 2-3 条支持原则（含设计测试）
    - principle: "Hand-drawn imperfection > polished 3D"
      design_test: 当新场景可以选"手绘感贴图"或"完美程序化生成"时，选手绘感
    - principle: "Warm colors on cold background create depth"
      design_test: 当 UI 颜色可以选红或蓝时，选和背景颜色对比大的
  color_philosophy:                # 色彩哲学
    palette_direction: "muted earth tones + one neon accent"
    semantic_meaning:
      "dark brown": "decay, old"
      "neon green": "life, mutation, hope"
```

**关键约束**：设计测试必须和 CD-PILLARS 的 Pillars 保持一致——Pillar "敏捷而非力量" 的设计测试是"选快速闪避而非堆攻击"，视觉方向的设计测试也必须服务于"敏捷"这个体验目标（比如"小而灵活的角色用快速闪白色轮廓"）。AD-CONCEPT-VISUAL 门禁的第三个检查就是"视觉方向能不能和 pillars 区分开"——即它是不是**基于 pillars 生成的视觉翻译**，还是另起炉灶。

#### 第二步：VIA 写入 game-concept.md（brainstorm Phase 7）

brainstorm Phase 7 写 game-concept.md 时，**在 Pillars section 之后、Player Types section 之前**插入一个新 section（full-concept.md 第 104 行明确写了位置）：

```markdown
## Visual Identity Anchor

> From AD-CONCEPT-VISUAL, approved [name of direction].

**One Rule:** beauty is in the decay

**Supporting Principles:**
1. **Hand-drawn imperfection > polished 3D** — Design test: when a new scene can be hand-drawn-textured or perfectly procedural, pick hand-drawn.
2. **Warm colors on cold background create depth** — Design test: when UI color can be red or blue, pick the one with more contrast against the background.

**Color Philosophy:**
- Palette direction: muted earth tones + one neon accent
- Semantic meaning: dark brown = decay/old, neon green = life/mutation/hope
```

**为什么写成散文而不是 YAML**：因为 game-concept.md 是给人读的设计文档，不是给机器读的配置。YAML 会让 concept 文件显得像一份配置表而不是一份设计说明书。但同时**保持了结构**——`**One Rule**:`、`**Supporting Principles**:`、`**Color Philosophy**:` 这些加粗的标题是 art-bible skill 用 Grep 定位的锚点。

#### 第三步：art-bible §3 从 game-concept.md 提取 VIA

art-bible SKILL.md 第 52-55 行规定了 VIA 的消费方式——它**不直接从 brainstorm 的输出里读**，而是**从 game-concept.md 里读**：

```markdown
### 1. Source: Concept Pillars + Visual Identity Anchor
   First, read `design/gdd/game-concept.md` and extract:
   - Pillars and their design tests (Phase 4)
   - Visual Identity Anchor section (from AD-CONCEPT-VISUAL)
   These two together form the **Vision Anchors** for the art bible.
```

**设计思路**：art-bible 不直接消费 brainstorm 的输出，而是消费 brainstorm **写入 game-concept.md 的那一版**。中间经过了"用户审查 concept 文档"这个环节——如果用户在 concept 评审时觉得 VIA 方向要改，改完 concept 再跑 art-bible，art-bible 读到的就是改后的版本。**concept 文档是所有下游技能的统一输入接口**，brainstorm 的输出必须经过 concept 文档才能到达 art-bible。

**为什么不用注册表中转**：VIA 不是跨系统事实（entities.yaml 记的是哥布林血量这种"多个 GDD 都引用的同一个值"），而是**一份完整的设计指令集**——它有结构但不是键值对，有段落但不是自由散文。放进注册表会被强行降格成"一条带字段的事实"，丢失设计测试的散文描述和语义。

#### 完整流转图

```
brainstorm Phase 4
  └─ AD-CONCEPT-VISUAL 门禁（召唤 art-director）
      └─ 产出 2-3 个视觉方向，每个含：
         name + one_rule + supporting_principles + color_philosophy
      └─ 用户选一个方向（或修订后锁定）
      └─ 判决：CONCEPTS / STRONG / CONCERNS

brainstorm Phase 7
  └─ 写 game-concept.md
      └─ 在 Pillars 和 Player Types 之间插入
         ## Visual Identity Anchor section
         （保持散文结构 + 加粗标题锚点）

art-bible SKILL.md §3
  └─ 读 game-concept.md 的 Visual Identity Anchor section
     （Grep "^## Visual Identity Anchor" 定位
      然后 Read 该节的 offset+limit）
  └─ 把它作为 §3 Color Philosophy 的
     种子输入（One Rule → 颜色选型的指导原则
              Supporting Principles → 设计测试
              Color Philosophy → 调色板方向 + 语义映射）
```

**零注册表中转的设计选择**：你可能会问——为什么不把 VIA 放进某个注册表（比如 `docs/registry/visual.yaml`），让 art-bible 直接 grep？因为 VIA 和 entities.yaml 里的"哥布林血量"本质不同：
- **哥布林血量**是一个**值**（40），被多个 GDD 用**键名**（goblin.health）引用——注册表的价值是"保证多个引用指向同一个值"；
- **Visual Identity Anchor** 是一套**设计指令集**，被 art-bible 用**段落内容**消费——它的消费方式是"读一遍，作为自己写 §3 的指导原则"，不是"拿键名查表取值"。

键值对场景用注册表，段落指导场景用**文档内嵌**——这也是这个项目文档设计的一条隐性规则。

## 6. 四个总监门禁的判决流（全链路图）

```
brainstorm Phase 4 ──► CD-PILLARS (creative-director)
                       │
                       ├─ APPROVE ──► 继续 Phase 5
                       ├─ CONCERNS ──► 修订 Pillars → 重跑 CD-PILLARS
                       ├─ REJECT ──► 修订 Pillars → 重跑 CD-PILLARS
                       └─ NOT ASSESSED ──► 补缺失输入 → 重跑
                                      ┌─ AD-CONCEPT-VISUAL (art-director)
                                      │  和 CD-PILLARS 并行
                                      │
                                      ├─ CONCEPTS ──► 用户选 2-3 个方向
                                      ├─ STRONG ──► 标记推荐项，用户确认
                                      └─ CONCERNS ──► 展示理由 + "修订 Pillars / 自己描述方向"
                                      │
                                      └─ Visual Identity Anchor 写入 game-concept.md
                                         → 成为 art-bible 的 §3 种子输入

brainstorm Phase 6 ──► TD-FEASIBILITY (technical-director)
                       │
                       ├─ VIABLE ──► 继续 Phase 7
                       ├─ CONCERNS ──► 记录 + 继续
                       ├─ HIGH RISK ──► 提供范围修订建议，用户决定改不改
                       └─ NOT ASSESSED ──► 补输入或记录为 NOT ASSESSED

brainstorm Phase 6 ──► PR-SCOPE (producer)
                       │  和 TD-FEASIBILITY 前后跑（同一个 Phase 6 里）
                       │
                       ├─ REALISTIC ──► 继续 Phase 7
                       ├─ OPTIMISTIC ──► 展示调整建议，用户决定是否应用
                       ├─ UNREALISTIC ──► 提供 MVP/范围修订选项，用户决定
                       └─ NOT ASSESSED ──► 补 timeline + team size 或记录

/map-systems Phase 3 ──► TD-SYSTEM-BOUNDARY (technical-director)
/map-systems Phase 4 ──► PR-SCOPE (producer，第二次)
/map-systems Phase 5 ──► CD-SYSTEMS (creative-director)
```

**关键规则**：
- solo/lean 模式下**所有四个门禁都跳过**（技能打印 `XXX skipped — Solo mode.` 然后继续）；
- **NOT ASSESSED 永远不是批准**——它表示"缺了什么导致我无法判断"，要么补输入重跑，要么记录下来（brainstorm 里的 TD-FEASIBILITY NOT ASSESSED 会把 feasibility 记为 not assessed，**永远不能**自动写 VIABLE；PR-SCOPE NOT ASSESSED 会记录 scope not assessed，**永远不能**自动写 REALISTIC）；
- **concept 永远不会因为门禁判决被拒绝**——TD-FEASIBILITY HIGH RISK、PR-SCOPE UNREALISTIC 都只提供修订建议，最终用户决定。唯一能让流程"卡住"的判决是 REJECT（CD-PILLARS 或 TD-SYSTEM-BOUNDARY 的 REJECT 意味着必须先修订才能继续）。

### 6.1 四个总监门禁的判决逻辑深化（NOT ASSESSED、跳过、跨门禁依赖）

#### solo/lean 模式的跳过实现：精确打印 + 直接进下一阶段

每个门禁在触发前**先检查 review_mode**——solo 和 lean 模式打印精确的跳过信息然后继续。代码模式都是这样（brainstorm full-concept.md 第 83-84 行）：

```markdown
**Review mode check:**
- `solo` or `lean`: print `CD-PILLARS skipped — Solo mode.` and go on to Phase 5.
- `full`: hand the pillar review to the `creative-director` agent...
```

**技术细节**：跳过不是"什么都不做"——它把判决**隐式降级为 APPROVE**（因为流程正常继续了），但**明确打印了跳过原因**。这让后续看代码或会话日志的人知道"这一步被跳过了，不是做了判决"，而不会误以为"总监认为没问题"。

#### NOT ASSESSED 的三种处理方式（每个门禁不同）

NOT ASSESSED 在每个门禁里的处理**不是统一的**——它取决于"缺了什么输入、这个输入能补不能补、补了之后重跑的代价"：

| 门禁 | NOT ASSESSED 的典型缺失 | 处理方式 |
|------|------------------------|---------|
| CD-PILLARS | 没有 Core Fantasy 或 Unique Hook | 列出缺失项 → 补充后重跑 CD-PILLARS；如果用户不想补则记录 `> Creative Director Pillar Review: NOT ASSESSED — [缺失项]` 在 concept 文件里 |
| AD-CONCEPT-VISUAL | 没有 pillar list 或没有 target platform | 列出缺失项 → 补充后重跑；**没有 AD 输出时**只给用户 `Describe my own direction` 一个选项（跳过 AI 推荐方向） |
| TD-FEASIBILITY | 没有 engine choice（"undecided"）或没有 platform | **永远不能**自动标记 VIABLE → 补充输入重跑，或记录 `> Technical Feasibility: NOT ASSESSED — [缺失项]`，**feasibility 永不标记为 VIABLE** |
| PR-SCOPE | 没有 timeline 或没有 team size | **永远不能**自动标记 REALISTIC → 补充输入重跑，或记录 `> Scope Reality: NOT ASSESSED — [缺失项]`，**scope 永不标记为 REALISTIC** |

**共同规则**：任何 NOT ASSESSED 都**绝对不能**被当作 APPROVE/VIABLE/REALISTIC——它只意味着"输入不够我无法判断"，不等于"我觉得还行"。门禁 prompt 里每个判决定义都写了"NOT ASSESSED is not an approval"。

#### 跨门禁依赖：CD-PILLARS 判决决定 AD-CONCEPT-VISUAL 怎么处理

full-concept.md 第 92-103 行有一个精确的条件分支——CD-PILLARS 的判决**直接决定了 AD-CONCEPT-VISUAL 的判决怎么被消费**：

```
IF CD-PILLARS == APPROVE:
    同时问两个问题：
    - Pillars: Lock in as-is / Revise / Discuss
    - Visual Anchor: 用户选方向（AD 返回的 CONCEPTS / STRONG）
    如果 AD 返回 STRONG → 标记 (Recommended)
    如果 AD 返回 CONCERNS → 展示理由 + "修订 Pillars / 自己描述方向"
ELSE IF CD-PILLARS == CONCERNS 或 REJECT:
    先单独解决 Pillars 问题
    Pillars 锁定后，再单独问 Visual Anchor 问题
ELSE IF CD-PILLARS == NOT ASSESSED:
    处理 CD NOT ASSESSED（补输入或记录）
    AD 的输出**降级处理**：如果没返回任何方向，只给用户 "Describe my own direction"
```

**设计思路**：CD-PILLARS 决定"游戏的灵魂"——如果灵魂还没站稳，先把灵魂搞对再选脸（AD-CONCEPT-VISUAL 输出）。灵魂站稳了，脸可以和灵魂一起讨论。CONCERNS/REJECT 意味着"支柱本身有问题"，而 AD-CONCEPT-VISUAL 返回的方向是基于**当前支柱**生成的——支柱有问题时基于它生成的方向自然也不可信，所以必须先修支柱。

#### "concept 永远不被拒绝" vs "REJECT 能卡流程"

这两个看似矛盾的规则背后是**门禁的目标差异**：

| 门禁 | REJECT 的含义 | 为什么能卡 | 为什么 concept 不会被拒 |
|------|--------------|----------|------------------------|
| CD-PILLARS | Pillars 太弱、不够用 | 支柱是整个概念的骨架——骨架弱了写出来的 concept 全是空话，必须先把支柱搞硬 | REJECT 只卡在"补 Pillars"这一步——不是"枪毙游戏想法"，而是"你得先想好我们为什么要做这个游戏"。补完继续 |
| TD-FEASIBILITY | HIGH RISK | 风险能让概念失效（"你想做的东西技术上根本做不到"） | **TD 门禁返回的不是 REJECT，而是 HIGH RISK**——名字就说明了它的语义：这是警告不是拒绝。技能只"offer to revisit scope"，用户决定改不改 |
| PR-SCOPE | UNREALISTIC | 范围太不现实 | **PR 门禁也不返回 REJECT**——它返回 UNREALISTIC，技能只"提供修订选项"，用户决定 |
| TD-SYSTEM-BOUNDARY | REJECT | 系统边界错到 GDD 写了也是返工 | 这是 `/map-systems` Phase 3 的门禁，还在 Phase 1 里——REJECT 意味着"边界必须先调对再写 GDD"，不是"枪毙游戏"。调完继续 |

**关键规律**：只有**架构/支柱类门禁**（CD-PILLARS、TD-SYSTEM-BOUNDARY）有 REJECT 判决；**范围/风险类门禁**（TD-FEASIBILITY、PR-SCOPE）返回的是**警告型判决**（HIGH RISK / UNREALISTIC）。警告不卡流程，REJECT 卡流程但只卡"补问题"那一步，永远不卡"游戏想法本身"。

## 7. 设计思路对照表（为什么这么做）

| 设计选择 | 直接原因 | 深层原理 |
|----------|----------|----------|
| brainstorm 分 minimal / standard / full 两条路 | 新用户被 full 流程吓退 | **渐进复杂度**：让不同经验的用户都能找到起点 |
| Lean Brief 硬卡 MVP ≤7 项 | 超过 7 项的 MVP 实际上不是 MVP | **反范围蔓延**：MVP 的定义是"最小能测核心循环的构建"，不是"我想做的所有东西" |
| Full Concept 的 Creative Discovery 从"人"出发 | 直接问"你想做什么游戏"得到模糊答案 | **从情感倒推规格**：用户说"我想让人感动"比说"我想做 RPG"更有价值 |
| Phase 2 三个生成策略必须混用 | 三个都用同一种就等于没发散 | **强制多样性**：避免 AI 倾向某一种生成模式导致三个概念本质相同 |
| Phase 3 四层循环 + SDT | 30 秒循环不满足→没爽点；SDT 任一需求没满足→玩家流失 | **从体验倒推机制**：这是 MDA 框架的直接应用 |
| Pillars 要有设计测试 | 没有它就是空口号 | **支柱可证伪**：设计测试让支柱在真实决策中能"选边" |
| 四个门禁判决都 ADVISORY | 流程卡住比"有点问题就过"更糟 | **人在环中**：AI 可以警告、建议、记录，但最终由用户拍板 |
| 跨阶段耦合（AD-CONCEPT-VISUAL → art-bible） | 美术圣经的 §3 需要 Visual Identity Anchor | **阶段间数据流动**：前一阶段的输出是后一阶段的输入，不是独立文档 |
| setup-engine 懒加载 references | 非 Godot 项目不读 Godot 配置文档 | **token 经济学**：按阶段懒加载，不加载不需要的文件 |
| project.yaml + technical-preferences.md 双写 | 旧消费者还在读 technical-preferences.md | **渐进迁移**：新单一事实源替代旧的过程中保持兼容 |
| Version Awareness section 注入 | 专家默认用训练数据里的旧 API | **模型知识 vs 项目知识解耦**：让专家先读项目特定参考文档 |
| art-bible retrofit 不加载完整文件 | 加载完整文件就是加载不会碰的内容 | **增量更新时节省上下文**：先 grep 结构再精确按节读 |
| NOT ASSESSED 永远不是批准 | 自动写 APPROVE/REALISTIC 会掩盖缺失输入 | **失败安全（fail-safe）**：宁可失败得响亮，不可悄悄假设 |

## 8. 术语表

| 术语 | 字面含义 | 在本阶段的确切意思 |
|------|----------|-------------------|
| **Lean Brief** | 瘦身版 brief | minimal 档的一页设计产出（design/game-brief.md），含 working title、pitch、core loop、MVP 列表、build order |
| **Game Concept** | 游戏概念 | standard/full 档的完整设计产出（design/gdd/game-concept.md），8+ 节 |
| **Creative Brief** | 创意简报 | brainstorm Phase 1 汇总的 3-5 句情感目标+品味+约束 |
| **Elevator Pitch** | 电梯对话 | 1-2 句能在 10 秒内讲清"这是什么游戏"的话 |
| **MDA Framework** | Mechanics-Dynamics-Aesthetics | 从玩家体验（Aesthetics）倒推系统（Mechanics）的三层设计框架 |
| **Core Loop（四层）** | 核心循环 | 30 秒 / 5 分钟 / Session / Progression 四层循环模型 |
| **SDT（Self-Determination Theory）** | 自我决定论 | 三个心理需求：自主 / 胜任 / 关联 |
| **Pillars + Anti-Pillars** | 支柱 + 反支柱 | 3-5 个设计支柱（每个有设计测试）+ 3+ 反支柱（"我们不会做 X"） |
| **Visual Identity Anchor** | 视觉身份锚 | AD-CONCEPT-VISUAL 门禁选出的视觉方向，brainstorm 写入 concept 并喂给 art-bible |
| **Knowledge Gap** | 知识缺口 | LLM 训练数据截止日期之后发布的引擎版本 → 需要 WebSearch 补 |
| **Dual-write** | 双写 | project.yaml（primary）+ technical-preferences.md（legacy mirror）同时写引擎配置 |
| **Version Awareness Section** | 版本感知章节 | 给引擎专家智能体注入的强制读项目参考文档的章节 |
| **NOT ASSESSED** | 未评估 | 门禁判决类型：输入缺失导致无法判断；**永远不能**当批准 |
| **Design-first vs Prototype-first** | 先设计 vs 先原型 | brainstorm Phase 8 的两条下一步路径：spec 先行 vs 核心机制先验证 |

## 9. 常见误区

1. **"minimal 档就是偷懒，concept 必须写全"**。错。minimal 档是为游戏 jam 和小项目设计的——一页 brief 的信息密度足够快速启动。项目长大以后可以升级 rigor，补全 GDD、systems-index、art-bible。现有文件不会丢。
2. **"autonomous 模式下 AI 应该替我选游戏方向"**。不对。Concept generation 阶段的三个 automation 档位**都必须让用户选方向**——autonomous 可以替用户拍技术决策，但不能替他拍"我想做什么游戏"。
3. **"Pillars 写得越多越好"**。反了。3-5 根支柱，互相有张力、每根都可证伪、都能帮解决设计分歧。超过 5 根等于没支柱。
4. **"NOT ASSESSED 可以当 REJECT 的反面——至少它没拒绝"**。完全错。NOT ASSESSED = "输入不够我无法判断"，不是"我觉得还行"。门禁定义里每处 NOT ASSESSED 的处理都是"补输入重跑或记录为 NOT ASSESSED"，**永远不能**写 APPROVE/REALISTIC。
5. **"TD-FEASIBILITY HIGH RISK / PR-SCOPE UNREALISTIC 意味着 concept 要被枪毙"**。不对。这两个判决**只提供修订建议**，用户决定改不改。只有 REJECT（CD-PILLARS / TD-SYSTEM-BOUNDARY）意味着流程必须先卡住——Pillars 弱到撑不起游戏，或系统边界错到 GDD 写了也是返工。
6. **"setup-engine 在 minimal 档比 brainstorm 晚跑"**。恰好相反——minimal path 里 setup-engine 是**第一步**（engine-setup → game-brief → create-stories → implement）。full path 里才是 brainstorm → setup-engine（因为 brainstorm 需要 concept 里的 platform 信息来推荐引擎）。
7. **"art-bible 必须先于 brainstorm 跑"**。反了。art-bible 的 §3 Color Philosophy 需要 brainstorm Phase 4 的 AD-CONCEPT-VISUAL 门禁输出作为种子——brainstorm 必须先跑完 Pillars 和视觉方向，art-bible 才能"有东西可写"。
8. **"design-review 和 brainstorm 门禁做同一件事，重复了"**。互补关系——brainstorm 门禁审**过程产物**（Pillars 列表、scope tiers 列表、风险列表这些结构化片段），design-review 审**最终文档**（整份 game-concept.md）。两者审的是不同对象、不同时机、不同粒度。

## 10. 小测验（答案都在上文）

**Q1**：brainstorm Phase 1 为什么先问 4 个开放性问题（"让你感动的游戏时刻"等）再问 3 个闭合选项？三个闭合选项为什么**必须一起问**？

> 答案：开放性问题从"人"出发，把模糊的"我想做游戏"变成具体的情感目标、品味、约束——比直接问"你想做什么游戏"得到的答案有质量得多。三个闭合选项（体验/时间/经验）必须一起问，因为它们是协同变量——选 "Multi-year" + "First game" 是不自洽的组合，需要在同一轮回答里暴露出来，而不是用户分别回答后 AI 才发现矛盾。

**Q2**：AD-CONCEPT-VISUAL 返回 CONCERNS 时，为什么解决方案是"修订 Pillars / 自己描述方向"而不是"继续现有方向"？

> 答案：AD-CONCEPT-VISUAL 返回 CONCERNS 的定义是"支柱没提供足够方向来区分视觉身份"——即 Pillars 里没有能"锚定"视觉方向的设计测试（比如 Pillar 写"敏捷"但没说敏捷在视觉上体现为什么）。所以"续现有方向"没用——支柱本身就是空的，方向没法锚定。解决方案要么是修订 Pillars（让支柱有视觉可锚定的内容），要么是跳过 AI 的方向建议、用户自己描述。

**Q3**：setup-engine 为什么要给引擎专家智能体注入 "Version Awareness" section？这解决了什么具体的"模型知识 vs 项目知识"问题？

> 答案：专家智能体默认知道"训练数据里的 Godot API"，但不知道"用户项目锁定的 Godot 4.7 API"——训练数据截止日期之后新增或废弃的 API，专家会用错。Version Awareness section 强制它每次给建议前先读项目特定的参考文档（VERSION.md / deprecated-apis.md / breaking-changes.md），把"模型知识"和"项目知识"解耦。setup-engine 的 §6 Knowledge Gap 检测 + §7 写参考文档 + §9 注入 section，三者形成完整的闭环。
