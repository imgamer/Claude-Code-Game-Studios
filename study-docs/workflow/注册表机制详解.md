# 注册表（Registry）机制详解 —— 为什么项目需要几本"总账"

> **一句话总览**：注册表是项目里**"同一个事实只允许有一个权威出处"**的记账本。`design/registry/entities.yaml` 记游戏世界里的事实（怪物属性、物品价格、公式、常量），`docs/registry/architecture.yaml` 记架构立场（谁拥有哪份状态、系统间怎么通信、性能预算、禁用的写法），`docs/architecture/tr-registry.yaml` 记需求的永久编号。它们共同解决一个朴素的问题：**当 30 份文档都提到"哥布林血量"时，你凭什么知道哪个数字算数、改动之后谁会受影响？**

本文依据 [entities.yaml](file:///workspace/design/registry/entities.yaml)、[architecture.yaml](file:///workspace/docs/registry/architecture.yaml)、[tr-registry.yaml](file:///workspace/docs/architecture/tr-registry.yaml)、[registry.sh](file:///workspace/.claude/scripts/registry.sh)、[validate-registry.sh](file:///workspace/.claude/hooks/validate-registry.sh)、[consistency-check/SKILL.md](file:///workspace/.claude/skills/consistency-check/SKILL.md)、[design-review/SKILL.md](file:///workspace/.claude/skills/design-review/SKILL.md)、[propagate-design-change/SKILL.md](file:///workspace/.claude/skills/propagate-design-change/SKILL.md)、[architecture-decision/CONTRACT.md](file:///workspace/.claude/skills/architecture-decision/CONTRACT.md) 等整理。

## 0. 先回答你最可能有的三个疑问

**疑问一：为什么我打开这两个文件是空的？**
因为它们出厂时就是**空骨架**：只有格式说明、规则和注释掉的示例，真正的条目由技能在写作时追加。`entities: []` 这个 `[]` 就是"本节还没有条目"的合法写法。项目里 `/design-system` 第 5b 步写完后才会往里加东西。所以"空"不是坏了，是"还没开始记账"。

**疑问二：既然是 YAML，为什么不用数据库？**
因为这里的"数据库"就是**仓库本身**：文件能进 git、能 diff、能在 PR 里被人逐行审阅、能被大模型用 `Read`/`Grep` 直接读。引入一个真数据库，反而会让"人和 AI 都能看懂"这件事消失。

**疑问三：它和上一份文档讲的"哈希回执"是什么关系？**
分工不同，见下表——这也是理解整套文档体系的关键：

| 机制 | 回答的问题 | 存的是什么 |
|------|------------|------------|
| **注册表**（本文） | 这个事实的**值是什么、谁说了算、谁在引用它** | 事实本身（血量 40、谁拥有 player_health） |
| **哈希回执**（[回填与哈希重跑机制](file:///workspace/study-docs/workflow/回填与哈希重跑机制.md)） | 这份结论是不是基于**眼前这版内容** | 内容的指纹，不存内容 |
| **ADR** | 当初**为什么**这样决定 | 决策与理由 |
| **control-manifest** | 写代码时要遵守哪些**约定** | 从 ADR 提取的规则清单 |

## 1. 初中生版：三本"花名册"的故事

想象一个班级要办运动会：

- 体育委员记了一份**参赛名单**（谁跑 100 米、谁跳远）；
- 生活委员记了一份**订餐表**（谁吃什么、交多少钱）；
- 班长记了一份**座位表**（谁坐第几排）。

三天后出问题了：体育委员写"小明参加 100 米"，生活委员写"小明对花生过敏"，班长写"小明坐第三排"——可小明的名字在三个本子上**写法都不一样**（"小明"/"李小明"/"明明"），电话也各不相同。老师想问"小明到底什么情况"，得把三个本子翻一遍，还可能翻出矛盾。

解决办法不是"让三个委员更仔细"，而是建一本**总册**：每个同学只登记一次，写清楚"谁负责维护这条记录"（source），以及"还有哪些本子引用了它"（referenced_by）。以后任何人要查小明，先查总册；任何人要改小明，先改总册，再按总册上记的引用清单去通知其他本子。

**这就是注册表的全部设计思路**。剩下的都是工程细节。

再换一个更贴切的比喻：**乐高说明书的零件表**。说明书里不会每一步都写"拿一块 2×4 的蓝色砖"，而是写"拿 2 号零件"。零件表里 2 号只定义一次，改了零件表，全书的步骤自动指向新零件——但如果某一步把"2 号"写成了"那块蓝的"，零件表就管不住它了。所以项目规定：**事实必须有名字，有名字就必须登记，引用时只写名字**。

## 2. 没有注册表，会发生什么（四个真实故障模式）

这些不是假想，文件头部的规则就是被它们逼出来的：

| 故障 | 场景 | 后果 |
|------|------|------|
| **影子副本** | 战斗 GDD 写"哥布林血量 40"，背包 GDD 为了写掉落表也抄了一遍"血量 40" | 策划把战斗改成 60，背包没改。两个文档都"看起来对"，代码照哪个写？ |
| **权威不明** | 两份 GDD 对同一公式给出不同系数 | 评审时无法裁决"谁错"，只能开会吵 |
| **引用断裂** | 需求编号 `TR-combat-003` 被重新编号成 `TR-combat-007` | 已经写进故事文件、测试报告的旧编号全部指向空气 |
| **隐形耦合** | 两个 ADR 都声称自己拥有 `player_health` 的写权限 | 运行时数据竞争，测不出来，上线才炸 |

注册表分别用四个字段对付它们：`source`（谁是权威）、`referenced_by`（谁在引用）、永久 ID（引用不断）、`state_ownership`（唯一写者）。**一句话：注册表把"靠人记得"变成了"靠结构保证"。**

## 3. 文件一：`design/registry/entities.yaml`（游戏世界事实）

### 3.1 它管什么

文件头第 1-5 行写得很直白：**"所有出现在一份以上文档里的、有名字的游戏世界事实"的单一事实源**。技能在写新内容之前先查它，从而在**写作时**就发现跨文档不一致。

四个分区，各管一类事实：

| 分区 | 管什么 | 举例 |
|------|--------|------|
| `entities` | 敌人、NPC、角色、阵营、Boss | 哥布林的血量、伤害、掉落 |
| `items` | 可收集物、装备、消耗品、材料、货币 | 哥布林手臂的售价、重量、能否堆叠 |
| `formulas` | 有具名变量和输出范围的公式 | 伤害公式、暴击公式 |
| `constants` | 被多个系统引用的具名数值 | 金币携带上限、初始背包格数 |

**注意它不记什么**（第 8-9 行）：只在单个 GDD 内部使用的公式**不用登记**。这条边界很重要——注册表一旦变成"什么都记"，就没人维护得动了。判断标准只有一条：**这个事实跨系统吗？**

### 3.2 逐字段解剖（以文件里注释掉的哥布林示例为蓝本）

```yaml
entities:
  - name: goblin
    status: active              # 生命周期
    source: design/gdd/combat.md
    referenced_by:
      - design/gdd/combat.md
      - design/gdd/inventory.md
    health: 40
    damage: 8
    drops:
      - item: goblin_arm
        qty: 1
        drop_rate: 0.8
    added: 2026-03-26
    revised: ""
```

| 字段 | 含义 | 为什么必须有 |
|------|------|-------------|
| `name` | 事实的**地址**（技能用 Grep 找它） | 没名字就无法被引用，也无法去重 |
| `status` | `active` / `deprecated` | 事实会过时，但**不能删**（见 3.3） |
| `source` | **权威 GDD**，这条事实"归谁所有" | 冲突时的裁决依据：改非 source 的那份 |
| `referenced_by` | 哪些文档引用了这条事实（块状列表） | 改值时知道要通知谁；不需要扫描全仓 |
| `health` / `damage` / `drops` … | **自由属性**：任何可能出现在别的 GDD 里的关键数值 | 这是"事实的正文" |
| `added` / `revised` | 登记日期 / 最后修订日期 | 追溯"什么时候变的" |

三个容易看漏的细节：

1. **`referenced_by` 里会出现 source 自己**（`combat.md` 既是 source 又是引用者）。这不是笔误：**拥有者也引用自己的事实**，保持列表完整，检索时才不会漏。
2. **属性是自由格式**。`health`、`damage`、`drops` 不是固定 schema，你可以加 `faction`、`armor_type`……这是刻意的取舍：**灵活优先，机器只校验结构（缩进、字段、状态值），不校验业务属性**。
3. **`drops` 里引用了 `goblin_arm`**，而 `goblin_arm` 必须在 `items` 分区有自己的条目（示例注释原文："must match an entry in items section"）。**注册表内部也互相引用**，这保证了"怪物掉什么"和"物品值多少钱"不会各说各话。

### 3.3 五条铁律（文件头第 7-16 行）

| 规则 | 原文含义 | 类比 |
|------|----------|------|
| 只记跨系统事实 | 单 GDD 内部的不记 | 只有需要跟别人对账的钱才上总账 |
| **永不删除，只标 `deprecated`** | 删了 = 历史断了 | 户口本不撕页，只注明"已迁出" |
| 改值要写旧值注释 | 更新 value、`revised:` 填今天、加注释说明旧值 | 账本改数要留划线痕迹 |
| `source` 是权威 | 其他 GDD 写进 `referenced_by` | 房产证只有一个名字 |
| 新增引用就追加，不复制条目 | 找到已有条目，往 `referenced_by` 里加自己 | 新同学登记到总册，不另开一本 |

## 4. 文件二：`docs/registry/architecture.yaml`（架构立场）

### 4.1 它管什么

文件头第 3-5 行：**"所有 ADR 都必须遵守的关键架构立场"的单一事实源**。技能在写新 ADR 之前先查它，**在故事被创建之前**就发现矛盾。

它和 entities 的最大区别：entities 记的是**游戏内容**（数值），architecture 记的是**建造方式**（结构约束）。六个分区，每个都对应一类"两个 ADR 可能打架"的冲突：

| 分区 | 管什么 | 不登记就会怎样 |
|------|--------|----------------|
| `state_ownership` | 每份共享状态**唯一的拥有者**和访问接口 | 两个 ADR 都写自己拥有 `player_health` → 数据竞争 |
| `interfaces` | 系统间通信的**约定模式**（signal / direct_call / event_bus / shared_resource / rpc / none） | 一个 ADR 发信号、另一个等直接调用 → 集成不上 |
| `performance_budgets` | 每个系统分到多少毫秒，总预算多少 | 各系统预算加起来超过 16.6ms → 根本跑不到 60 帧 |
| `api_decisions` | 某个用途**选定哪个引擎 API**（以及禁用哪个） | 两个 ADR 对同一件事用不同 API → 行为不一致 |
| `forbidden_patterns` | 被明确禁止的反模式（如直接引用 Autoload 单例） | 新 ADR 无意中用了禁区写法 → 返工 |
| （`version` / `last_updated`） | 文件自身版本 | — |

### 4.2 逐字段解剖（状态所有权示例）

```yaml
state_ownership:
  - state: player_health
    status: active
    owner_system: health-system
    adr: docs/architecture/adr-0001-health-system.md
    interface: "HealthComponent.current_health (read-only float, range 0–max_health)"
    write_access: health-system-only
    referenced_by:
      - docs/architecture/adr-0001-health-system.md
      - docs/architecture/adr-0003-combat-system.md
      - docs/architecture/adr-0007-ui-system.md
    added: 2026-03-26
    revised: ""
```

| 字段 | 含义 | 设计意图 |
|------|------|----------|
| `state` | 状态的具名标识 | 这是主键，Grep 用它 |
| `owner_system` | **唯一拥有者** | 回答"谁说了算" |
| `adr` | 权威 ADR（相当于 entities 的 `source`） | 冲突时以它为准 |
| `interface` | 别人**怎么访问**（只读属性/方法/信号/共享资源） | 这是其他 ADR 依赖的"合同" |
| `write_access` | 谁可以写（通常只有拥有者） | 防"越权写" |
| `referenced_by` | 哪些 ADR 依赖这个立场 | 改立场时知道谁要复审 |

`interfaces` 分区的主键叫 `contract`（合同名），`performance_budgets` 的主键是 `system` 或 `target_fps`，`api_decisions` 的主键是 `purpose`，`forbidden_patterns` 的主键是 `pattern`。**每个分区用"最能代表它身份的那个字段"当第一行**——这不是随意的，是 [registry.sh](file:///workspace/.claude/scripts/registry.sh#L338-L345) 硬编码读取的规则（见第 6 节）。

### 4.3 一条特别值得学的规则

文件头第 11-12 行：

> Never delete entries — set `status: "superseded_by: ADR-NNNN"` instead, **quoted**: unquoted, the second colon makes the file invalid YAML.

翻译：作废不是删除，而是标 `superseded_by: ADR-NNNN`；而且**必须加引号**，因为值里出现了第二个冒号，不加引号 YAML 解析器会把它当两个键，整份文件直接非法。这条规则还催生了一个兼容逻辑：`registry.sh` 会识别 1.2.0 之前的旧写法（没加引号的），把它读出来并**提示你去加引号**，而不是整个文件罢工（[registry.sh 第 449-455、460-461 行](file:///workspace/.claude/scripts/registry.sh#L449-L461)）。**这是"向后兼容一个已知错误写法"的教科书式处理**：能读就继续读，但要提醒。

## 5. 文件三：`docs/architecture/tr-registry.yaml`（需求编号）

虽然你没问，但它是同一家族里最容易被误解的一个，必须一起讲。

**它解决的问题**：`/architecture-review` 每次运行都会从 GDD 里"提取技术需求"。如果每次重新编号，第一次是 `TR-combat-001`，第二次因为顺序变了变成 `TR-combat-003`——已经写进故事文件的编号就全错了。所以：

- **ID 永久**：格式 `TR-[system]-[NNN]`，每个系统独立三位序号，从 001 开始（[tr-registry.yaml 第 27-31 行](file:///workspace/docs/architecture/tr-registry.yaml#L27-L31)）；
- **只追加**：新条目只能加在每个系统列表的**末尾**；
- **改措辞不改 ID**：需求表达调整（意思不变）→ 更新 `requirement` 文本、填 `revised`，ID 不变；
- **删需求不删条目**：`status: deprecated`；
- **拆分/替代**：`status: "superseded-by: TR-combat-001"`（同样必须加引号）；
- **禁止重新编号**（第 8 行原文："IDs are PERMANENT. Never renumber, never delete"）。

**为什么编号比文字更重要**：故事文件、测试报告、追溯矩阵里引用的都是编号。编号稳定，引用就永远能解析到"当前这条需求是什么"；文字可以改，编号不动。这就像身份证号——你改名换地址，号不变。

`/dev-story` 有一条很关键的规定：实现故事时，**以 `tr-registry.yaml` 里的 `requirement` 文本为准，而不是故事文件里抄的那段**（[dev-story/SKILL.md 第 161-163 行](file:///workspace/.claude/skills/dev-story/SKILL.md#L161-L163)）。这又是一次"拒绝影子副本"。

## 6. 格式解析：为什么写成这个样子

### 6.1 核心设计：为 Grep 而生，不是为 YAML 解析器而生

文件头第 45-47 行有一句关键的话：

> **FORMAT**: YAML. Consistent indentation is critical for **grep reliability**.

以及第 49-54 行的 `LAYOUT` 说明：**"这是 `.claude/scripts/registry.sh` 唯一能读的形状"**。

也就是说：这份 YAML 的首要消费者不是 PyYAML，而是 **Grep 和大模型**。所以它刻意保持"**一行一个事实**、**缩进固定**、**不用复杂的嵌套**"。代价是写法受限，收益是：任何技能、任何语言、任何工具都能用一行 `grep` 精确捞出一条记录，不需要先解析整个文件。

### 6.2 四条布局规则（记住这四条就能读懂所有注册表）

| 规则 | 正确写法 | 说明 |
|------|----------|------|
| **分区键在第 0 列** | `entities:` 顶格 | 整个文件的分区列表 |
| **条目的 `-` 在第 0 列或第 2 列，且同一分区内统一** | `  - name: goblin` | 两种列号都被支持，但**一个分区里不能混用** |
| **字段比 `-` 再深 2 列** | `    source: ...`（`-` 在 2 列，字段在 4 列） | 层级靠缩进表达，深一行就属于上一行 |
| **值里含 `": "` 必须加引号** | `status: "superseded_by: ADR-0001"` | 否则第二个冒号会让 YAML 非法 |

### 6.3 其余格式细节

| 场景 | 写法 | 原因 |
|------|------|------|
| 分区暂时为空 | `entities: []` | 显式声明"空"，而不是留一个孤零零的键 |
| `referenced_by` 是列表 | 块状列表（每项一行 `- 路径`）或单行流式 `[a, b]` | 块状更好 diff；流式适合短列表 |
| 多行长文本 | `notes: \|` 或 `notes: >` | 块标量里的行**永远不会被当成字段或条目** |
| 缩进 | **只能用空格，不能用 Tab** | Tab 会让列号计算错位，直接被判 LAYOUT |
| 列表写在字段下方 | 比字段再深即可 | "深于键的行属于它" |

### 6.4 会被判"布局不支持"的写法（registry.sh 会报行号）

```
- 条目 `-` 在第 4 列                      → 只支持第 0 或第 2 列
- 同一分区里条目缩进不一致                → 必须全部对齐
- 字段写在 `-` 的左边或与 `-` 同列          → 必须比 `-` 深 2 列
- 未加引号且值里含 ": "                    → 会被当成两个键
- 流式列表跨行（[a, 换行 b]）              → 必须写在一行内
- 用 Tab 缩进                              → 直接报错
```

**为什么这么严格**：因为 `registry.sh` 用 awk 逐行读，它不做完整 YAML 解析。**布局就是 API 契约**——布局一乱，脚本宁可报"读不懂"也不猜，避免把错误数据喂给技能。这是"**宁可失败得响亮，不可悄悄读错**"的工程取舍。

## 7. 实际如何发挥作用（全链路）

### 7.1 谁写、谁读（文件头部就是权威清单）

**entities.yaml**（第 18-32 行）：

| 角色 | 谁 |
|------|-----|
| 写入 | `/design-system`（第 5b 步，GDD 章节批准后）、`/consistency-check`（解决冲突时）、`economy-designer` / `systems-designer`（问过用户后加新条目） |
| 读取 | `/design-system`（第 2 步写作前、写完 C/D 节后查冲突）、`/consistency-check`（主要输入，先查注册表再查 GDD）、`/review-all-gdds`、`/design-review`（替代读兄弟 GDD）、`/content-audit`、`/balance-check`、`/propagate-design-change`、`/asset-spec`、经济/系统设计师 |

**architecture.yaml**（第 19-24 行）：

| 角色 | 谁 |
|------|-----|
| 写入 | `/architecture-decision`（第 5 步，ADR 批准后） |
| 读取 | `/architecture-decision`（第 2 步，写作前查冲突）、`/architecture-review`（第 4 步，跨 ADR 冲突基线）、`/create-stories`（把架构约束嵌进故事）、`/dev-story`（对照已接受的立场检查实现） |

**tr-registry.yaml**（第 17-25 行）：由 `/architecture-review` 追加；被 `/create-stories`、`/dev-story`、`/story-done`、`/story-readiness`、`/create-epics`、`/test-helpers`、`/adopt`、`/create-architecture` 读取。

### 7.2 统一读取器：`registry.sh`

项目不让每个技能自己写一套 grep，而是提供 [registry.sh](file:///workspace/.claude/scripts/registry.sh)（第 2-7 行原话："**让每个技能用同样的方式读同样的条目**"）。它支持三种注册表 `entities` / `tr` / `architecture`，共 7 个命令：

| 命令 | 干什么 | 典型调用 |
|------|--------|----------|
| `list [注册表] [--system 系统]` | 每条一行 | 浏览全部实体；只看某系统的 TR |
| `get 名字...` | 打印指定条目的**原始行**（不是摘要） | 查一条事实的完整上下文 |
| `refs 名字\|路径` | 反向查引用：谁引用了它 / 某个 TR 被哪些故事引用 | 改之前评估影响面 |
| `slice 路径` | 打印所有"来源/引用"指向该路径的条目**整条** | `/design-system` 第 2 步：`registry.sh slice design/gdd/combat-system.md` |
| `validate` | 查重复名、故事里引用了但注册表没有的 TR、不存在的路径、非法状态值、非法布局 | 每次写完注册表都跑 |
| `compare 注册表 旧文件 [新文件]` | 对比写入前后的注册表：被删的条目、非法状态、布局问题 | 被 PreToolUse 钩子调用 |
| `next-id 类型 [范围]` | 算下一个可用编号 | ADR / BUG / ASSET / TD / story / sprint / season / TR |

两条设计原则：

1. **只报观察，不下判决**（第 9-11 行）。脚本输出 `ENTRY` / `REF` / `DUPLICATE` / `PATH_MISSING` 这些**事实行**，至于"这个缺失要不要阻止流程"，由调用它的技能按自己的规则决定。和哈希脚本一样：**机制层报事实，策略层做决定**。
2. **`next-id` 防止编号复用**：它算的是"见过的最大编号 + 1"（第 36-37 行），不是"当前条目数 + 1"。所以删掉或废弃过的编号**永远不会被重新发放**——这正是"引用永不指向错误对象"的保证。

### 7.3 写前守卫：PreToolUse 钩子

[validate-registry.sh](file:///workspace/.claude/hooks/validate-registry.sh) 挂在对 Write/Edit 的 **PreToolUse** 上，专门守 `entities.yaml` 和 `tr-registry.yaml`：

1. 只看这两份文件（第 58-61 行，其他写入直接放行，几乎零开销）；
2. 用 `hook-input.sh` **重建"写入后的新内容"**——因为 Edit 只给 `old_string`/`new_string`，必须自己拼出结果；
3. 调用 `registry.sh compare 旧路径 新文件`；
4. 如果新内容**删掉了条目**、出现了**非法状态值**、或**布局读不懂**，就打印警告。

关键点：**它永远 exit 0，只是建议性警告，不阻止写入**（第 46-47 行）。这是项目的统一风格——钩子负责"让你知道"，最终决定权在你。同时第 42-44 行提醒：钩子不是万能的，**技能写完后仍必须自己跑一次 `validate`**，因为钩子不会覆盖所有执行路径。

### 7.4 一条完整时间线：哥布林的一生

```
① /design-system combat
   写完 GDD → 第 5b 步登记 goblin（source: combat.md）→ 跑 validate

② /design-system inventory
   第 2 步跑 registry.sh slice design/gdd/inventory-system.md
   → 看到 goblin / goblin_arm 是"已知事实"，把它当成必须遵守的既有决策
   → 写背包 GDD 时直接引用，不再自己定义一遍血量

③ /design-review design/gdd/combat-system.md
   不再读兄弟 GDD 去"重新发现"事实，而是按注册表核对（设计评审原文：
   "prefer the registry over sibling GDDs"）；哈希验章清单里也包含 entities.yaml
   → 注册表变了，评审结论同样要复核

④ /consistency-check
   先查注册表，再查 GDD → 发现背包 GDD 写"血量 60"、注册表说 40
   → 判 🔴 CONFLICT（或 ⚠️ STALE REGISTRY）
   → 按 source 裁决：改非权威的那份；改注册表时留下 "# was: 40 before 2026-xx-xx"

⑤ 战斗 GDD 把哥布林血量改成 60
   → /propagate-design-change
     用 git diff 看改了哪节；用注册表 source 找到这条事实；
     按 referenced_by 列出所有下游 GDD 名单 → 逐个核对

⑥ /architecture-review
   从 GDD 提取技术需求 → 追加 TR-combat-001（已存在则复用，绝不重新编号）

⑦ /create-stories
   把 TR-combat-001 嵌进故事文件 → /dev-story 实现时以注册表里的需求原文为准

⑧ /story-readiness / /story-done
   校验 TR-combat-001 存在且 status: active；需求被拆分了就查 superseded-by
```

这条链串起来就是：**登记 → 引用 → 评审 → 一致性检查 → 变更传播 → 编码 → 结项**。注册表不是某一阶段的产物，而是**横穿整个流程的公共基础设施**。

### 7.5 和门禁的关系

注册表本身不判 PASS/FAIL，但多个门禁会**消费**它：

- Technical Setup 门禁要求"没有过期的 GDD 引用"（老 GDD 要回填新决策，见 [回填与哈希重跑机制](file:///workspace/study-docs/workflow/回填与哈希重跑机制.md)）；
- Pre-Production 门禁要求 ADR 对引擎版本、架构立场一致；
- `workflow: full` 下 `/dev-story` 若缺 TR 注册表会**直接停下**，提示先跑 `/architecture-review`（[dev-story/SKILL.md 第 69-73 行](file:///workspace/.claude/skills/dev-story/SKILL.md#L69-L73)）。

## 8. 还有哪些"同类文档"（单一事实源家族）

项目里"一本总账管一类事实"的思路反复出现。认全这个家族，你就能看懂大部分"为什么这里要单独一个文件"：

| 文件 | 管什么事实 | 谁写 | 谁读 | 为什么也需要它 |
|------|-----------|------|------|----------------|
| [design/registry/entities.yaml](file:///workspace/design/registry/entities.yaml) | 游戏世界数值事实 | `/design-system`、`/consistency-check` | 几乎所有设计技能 | 防止数值复制到多份 GDD 后漂移 |
| [docs/registry/architecture.yaml](file:///workspace/docs/registry/architecture.yaml) | 架构立场 | `/architecture-decision` | `/architecture-review`、`/create-stories`、`/dev-story` | 防止多个 ADR 互相矛盾 |
| [docs/architecture/tr-registry.yaml](file:///workspace/docs/architecture/tr-registry.yaml) | 需求编号与原文 | `/architecture-review` | `/create-stories`、`/dev-story`、`/story-*` | 防止需求编号被重排导致引用断裂 |
| `docs/architecture/control-manifest.md` | 编码约定（每层允许/禁止什么、命名、禁用的 API） | `/create-control-manifest` | `/create-stories`、`/dev-story` | 把 ADR 的"立场"翻译成"写代码时逐条可查的规则"；带 `Manifest Version` 日期，故事会记下自己基于哪版 |
| [systems-index.md](file:///workspace/.claude/docs/templates/systems-index.md) | 有哪些系统、优先级、依赖、设计状态 | `/map-systems` | `/design-system`、`/help`、`/create-epics` | 决定"先设计哪个系统"，是设计阶段的排队表 |
| `production/epics/index.md` | 有哪些史诗（Epic）及状态 | `/create-epics` | `/create-stories`、`/help` | 故事的上一级索引 |
| `design/assets/asset-manifest.md` | 资产编号与规格索引 | `/asset-spec` | 美术/音频流程 | `registry.sh next-id asset` 就是从这里取 `ASSET-NNN` |
| `docs/tech-debt-register.md` | 技术债编号 `TD-NNN` | 各技能 | 评审、发布门禁 | 债务也要有稳定编号才能追踪 |
| [project.yaml](file:///workspace/project.yaml) | 项目配置 | `/start`、`/settings` | 所有技能 | 配置的单一事实源（详见 [配置体系与rigor心智模型](file:///workspace/study-docs/workflow/配置体系与rigor心智模型.md)） |

**共同的三条设计特征**（认这个比认文件名更有用）：

1. **一个事实只定义一次**，其他文件只引用它的名字/编号；
2. **只追加、不删除**，用状态字段表达生命周期（`deprecated` / `superseded_by`）；
3. **布局固定、可被 grep**，所以既给人读，也给脚本和模型读。

## 9. 术语表（字面语义 + 项目含义）

| 术语 | 字面含义 | 在这个项目中的确切意思 |
|------|----------|----------------------|
| **Registry** | 登记处、注册表 | 一份记录"具名事实"及其归属/引用的台账文件 |
| **Single Source of Truth（SSOT）** | 单一事实源 | 同一个事实只允许一个权威出处，其他位置只能引用 |
| **source** | 来源 | entities 里指"拥有这条事实的 GDD"；architecture 里等价字段叫 `adr`；tr 里叫 `gdd` |
| **referenced_by** | 被谁引用 | 反向依赖清单；改值时按它通知下游，不用扫描全仓 |
| **owner_system** | 拥有系统 | 唯一有权写入某份共享状态的系统 |
| **contract** | 合同 | 系统间通信的约定模式（信号/直接调用/事件总线…） |
| **stance** | 立场 | ADR 中"必须被其他系统遵守"的架构约束 |
| **superseded_by** | 被……取代 | 旧条目作废的标准写法；**必须加引号**，否则 YAML 非法 |
| **deprecated** | 已废弃 | 条目仍保留在文件中，但不该再被新内容引用 |
| **append-only** | 只追加 | 只能新增，不能删除或重排；是编号稳定性的前提 |
| **manifest** | 清单、舱单 | 从 ADR 提取的编码规则清单（control-manifest） |
| **backfill / retrofit** | 回填 | 给已有文件补缺失内容；见 [回填与哈希重跑机制](file:///workspace/study-docs/workflow/回填与哈希重跑机制.md) |
| **LAYOUT** | 版式 | `registry.sh` 对"读不懂的行"的报告类型，附行号和期望写法 |
| **grep-first** | 先 grep | 检索策略：先用注册表定位，再只读命中的那一段，而不是整份文档通读 |

## 10. 常见误区

1. **"注册表是自动生成的，我不用管"**。错。它由技能在特定步骤**追加**，且每次写完都要跑 `validate`；钩子只警告，不代劳。
2. **"条目没用了就删掉"**。绝对不行。删了会让历史引用悬空；正确做法是 `status: deprecated`，被替代则写 `superseded_by`。
3. **"名字随便写，反正人能看懂"**。名字是主键，是 Grep 的地址。同一条事实写两个名字（`goblin` / `Goblin`）在机器看来就是两条，去重和引用都会失效。
4. **"注册表里没查到，说明这个事实不存在"**。不一定。注册表是**空骨架起步**的，只在"跨系统事实"登记后才非空；查不到也可能是"还没登记"。
5. **"注册表能保证数值一定正确"**。不能。它保证的是"**只有一个权威值，且引用关系清楚**"；值本身对不对，要靠评审和测试。
6. **"architecture.yaml 和 control-manifest.md 是一回事"**。前者是**架构立场**（谁拥有状态、怎么通信），后者是**编码约定**（每层能写什么、命名怎么起、哪些 API 禁用）。前者是"宪法"，后者是"员工手册"。
7. **"YAML 嘛，我随便排一下版也行"**。不行。缩进、引号、Tab 都是 API 契约；布局一坏，`registry.sh` 读不出条目，等于这份注册表对技能"不存在"。
8. **"有了注册表就不用读 GDD 了"**。错。注册表只存**跨系统摘要事实**，完整的规则、边缘情况、验收标准仍在 GDD 里；注册表是索引，不是替代品。

## 11. 小测验（答案都在上文）

**Q1**：为什么 `entities.yaml` 要求"永不删除条目"，而不是"删掉过期条目保持整洁"？

> 答案：因为条目被其他文档、故事、报告引用。删除会让引用指向不存在的事实，历史也无从追溯。用 `status: deprecated` 保留条目，既表达了"不要再用"，又保住了引用链和历史——和需求编号"永不重排"是同一个道理。

**Q2**：`registry.sh` 的 `next-id` 为什么用"见过的最大编号 + 1"，而不是"当前条目数 + 1"？

> 答案：条目会被废弃，但编号不能被重新发放。如果按条目数算，废弃一条后新条目会拿到旧编号，导致历史引用指向错误对象。取最大值 + 1 保证编号单调递增、永不复用。

**Q3**：为什么 `architecture.yaml` 的 `status: "superseded_by: ADR-0001"` 必须加引号？

> 答案：值里含有第二个 `": "`。不加引号，YAML 会把它解析成嵌套的键值，整份文件变成非法 YAML。`registry.sh` 对旧版没加引号的写法做了兼容读取，但会提示你补引号。
