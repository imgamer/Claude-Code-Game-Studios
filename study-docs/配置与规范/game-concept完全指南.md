## 0. 先记住五句话

1. `game-concept.md` 是**概念阶段的产物**：用一页纸回答"这个游戏是什么、给谁玩、凭什么好玩、做多大"。
2. 它由 `/brainstorm` 技能引导你**分阶段问答生成**，最终写到 `design/gdd/game-concept.md`；模板只是"表格的空壳"。
3. 它是一份**决策文档**：写给创意总监（creative-director）审批、写给概念门禁（gate-check）检查——批准之后基本冻结，很少改动。
4. 它的方法论核心是**从玩家的感受倒推要做的系统**（MDA 框架），而不是先想功能再凑乐趣。
5. 它内含的"Pillars（支柱）"只是**种子摘要**；真正全程被反复引用的展开版在 `design/gdd/game-pillars.md`——两份文档是"立项书"和"团队信条"的关系（详见第 6 节）。

## 1. 这份文档是什么，不是什么

### 1.1 一句话定义

`game-concept.md` 是游戏的**立项书**：在写任何详细设计之前，把"这是个什么游戏"讲清楚，让团队和 AI 代理判断它值不值得继续做、怎么做才不跑偏。

它住在两个地方，角色不同：

| 位置 | 角色 |
|---|---|
| `.claude/docs/templates/game-concept.md` | **模板**：带引导注释的空表格，由技能复制使用 |
| `design/gdd/game-pillars.md` 旁边的 `design/gdd/game-concept.md` | **工作副本**：/brainstorm 问答后写入的真实文档 |

### 1.2 边界表

| 它是 | 它不是 |
|---|---|
| 一份"为什么做、做什么、做多大"的决策依据 | 详细设计文档（那是各个系统 GDD 的工作） |
| 概念门禁的检查对象 | 技术配置（那是 `project.yaml` 和 CLAUDE.md 的工作） |
| 从玩家体验出发的分析（MDA、SDT、心流） | 功能清单或愿望清单 |
| 带风险与缩水预案的商业计划 | 合同或不可修改的圣旨（Status 会走 Draft → Approved） |
| 后续所有设计的"源头引用" | 只写一次就没人看的存档（map-systems、gate-check 都会回头读它） |

### 1.3 谁写、谁读

| 角色 | 行为 |
|---|---|
| `/brainstorm`（写入者） | 分 8 个阶段问答，征得同意后写入 `design/gdd/game-concept.md`；已存在时按章节续写而不是重来 |
| `creative-director`（审批者） | 审批概念与支柱；概念获批是进入下一阶段的条件之一 |
| `/design-review`（评审者） | 检查概念文档是否完整、自洽 |
| `/gate-check`（门禁） | 概念阶段 → 系统设计阶段的门禁会读取它做评估 |
| `/map-systems`（分解者） | 把获批概念拆解成系统清单（systems index） |
| `/prototype`、`/vertical-slice`、`/playtest-report`（验证者） | 加载概念来对齐"要验证的核心假设" |
| `/setup-engine`（配置者） | 引导模式会读概念里的引擎推荐，帮你填技术栈 |
| `project-stage-detect`、`review-scope.sh`、`validate-commit.sh` 等脚本 | 用它的存在与否判断阶段与范围 |

一句话：**写它的是一次头脑风暴，读它的是整个流水线。**

## 3. 术语白话词典

按文档中出现的顺序排列。"白话"一栏给非专业读者，"准确含义"一栏保留专业表达。

| 术语 | 白话 | 准确含义 |
|---|---|---|
| **Elevator Pitch（电梯陈述）** | 和投资人同乘电梯的 30 秒里，讲清这是个什么游戏 | 1–2 句话概括整个游戏，公式："这是一个[类型]游戏，你在[场景]里[核心动作]，为了[目标]" |
| **Core Identity（核心身份）** | 游戏的"户口本" | 类型、平台、目标人群、人数、单局时长、收费模式、规模、对标游戏的结构化表格 |
| **Genre / Subgenre** | 游戏的"菜系"：主类型和小分支 | 如"Roguelike + 种田" |
| **Comparable Titles（对标游戏）** | "我们家游戏像谁" | 2–3 款同赛道已有游戏，用来定位与沟通 |
| **Session Length（单局时长）** | 玩家一次坐下来玩多久 | 10 分钟 / 30 分钟 / 1 小时 / 2 小时以上 |
| **Monetization** | 怎么收钱 | 买断 Premium / 免费+内购 F2P / 订阅 / 未定 |
| **Core Fantasy（核心幻想）** | 玩家在这个游戏里"成为谁" | 玩家获得的情感承诺——"为什么选这个游戏而不是别的" |
| **Unique Hook（独特钩子）** | "就像 X，而且还 Y"的那个 Y | 与同类型一切游戏区分开的单一最重要差异点 |
| **"and also" 测试** | 检验钩子灵不灵的口诀 | "它像[对标]，**而且还**[独特点]"——"而且还"不让人好奇，钩子就没写好 |
| **MDA 框架** | 从"想让玩家感受到什么"倒推"该造什么机器" | Mechanics（规则）→ Dynamics（涌现行为）→ Aesthetics（体验感受）的设计分析法 |
| **Aesthetics（审美/体验目标）** | 玩戏时的心情种类 | MDA 的 8 类：感官、幻想、叙事、挑战、交际、探索、表达、放松 |
| **Dynamics（动态行为）** | 玩家没被教、自己"玩出来"的行为 | 机制之间相互作用涌现出的玩家行为模式 |
| **Mechanics（机制）** | 我们实际建造的"游戏规则零件" | 3–5 个支撑上述体验的核心系统 |
| **SDT（自我决定理论）** | 人为什么会"想继续玩"的三种心理粮食 | 自主感 Autonomy、胜任感 Competence、联结感 Relatedness |
| **PENS** | SDT 在游戏里的翻版 | Player Experience of Need Satisfaction，玩家需求满足模型 |
| **Bartle 玩家类型** | 玩家的四种"人格" | 成就者、探索者、社交者、杀手/竞争者 |
| **Flow（心流）** | 玩到忘记时间的状态 | 挑战与技能匹配时的高度专注；靠入门曲线、难度爬坡、清晰反馈、快速失败恢复来维持 |
| **Core Loop（核心循环）** | 玩家反复做的那个"圈" | 分四个时间尺度：30 秒 / 5–15 分钟 / 一整局 / 长期成长 |
| **Retention Hooks（回头钩子）** | 明天为什么还会打开它 | 好奇、投入、社交、精进四类 |
| **Pillars（支柱）** | 压倒一切的设计原则，吵不出结果时它说了算 | 3–5 条不可协商的原则；两案冲突时用来裁决 |
| **Anti-Pillars（反支柱）** | 明确宣布"这游戏不是什么" | 防止范围蔓延的"不许做"清单；每个"不"都在保护一个"是" |
| **Design Test（设计测试）** | 检验支柱能不能"断案"的一道真题 | 一条具体争论："如果纠结 X 还是 Y，这条支柱判我们选 __" |
| **Target Player Profile（目标玩家画像）** | 把"目标用户"具体到一个真人 | 年龄、经验、时间、平台、正在玩什么、缺什么、什么会劝退 |
| **Art Pipeline（美术管线）** | 美术资产的生产难度 | 低（改素材库）/ 中（定制 2D）/ 高（定制 3D） |
| **Procedural Systems（程序化生成）** | 让电脑自动造内容的系统 | 如随机地牢；这里只估范围，不设计细节 |
| **MVP（最小可行版本）** | 只回答"核心循环好不好玩"的最小版本 | 验证单一核心假设所需的最少功能集 |
| **Vertical Slice（垂直切片）** | 一小块"完整层蛋糕" | 一个做完的内容切片：所有系统都通、但内容只有一小段 |
| **Scope Tiers（范围档位）** | 钱和时间不够时的"缩水预案" | MVP → Vertical Slice → Alpha → Full Vision 四档 |
| **Open Questions（开放问题）** | 现在还答不了、需要先做实验的问题 | 每条要附"打算用什么原型来回答它" |

## 4. 逐节精讲

模板共 13 个正文小节。每一节按"白话是什么 → 为什么存在 → 填写要点 → 常见错误"来讲。

### 4.1 Elevator Pitch（电梯陈述）

- **是什么**：整个游戏压进 1–2 句话。
- **为什么**：如果一句话讲不清，通常说明想法还没想清。这句话之后会被所有文档、所有代理反复引用。
- **要点**：套公式"这是一个[类型]游戏，你在[场景]里[核心动作]，为了[目标]"；用"10 秒测试"自检——没听说过这游戏的人 10 秒内能明白自己将要干什么吗。
- **常见错误**：写成功能罗列（"有 crafting、有roguelike、有多人……"）；形容词堆砌（"史诗级沉浸体验"）。

### 4.2 Core Identity（核心身份）

- **是什么**：一张 8 行的"户口本"表格。
- **为什么**：把最容易吵架的八个事实一次性钉死。后面每个阶段（引擎选择、美术预算、联网架构）都在消费这张表。
- **要点**：Estimated Scope 要写"小/中/大 + 月份 + 人手"，不许只写"大"；Comparable Titles 给 2–3 款真实存在的游戏。
- **常见错误**：Target Audience 填"玩家"（模板自己都吐槽了：**"Gamers" is not a target audience**——"玩家"不是目标人群）。

### 4.3 Core Fantasy（核心幻想）

- **是什么**：玩家的情感承诺：在这里他能成为谁、感受到什么。
- **为什么**：这是"为什么选这个游戏"的终极答案。功能会被抄袭，幻想是灵魂。
- **要点**：模板给了四个范例句式（孤胆幸存者、文明的统治者、自在的探索者、征服不可能的武者）。写"感觉"，不写"功能"。
- **常见错误**：写成功能列表——模板原话："It's not a feature list"（它不是功能清单）。

### 4.4 Unique Hook（独特钩子）

- **是什么**：与同类型所有游戏区分开的那个"**而且还**"。
- **为什么**：没有钩子的游戏没有存在的理由，只有"还行的复制品"。
- **要点**：一句话能讲清；真的新颖（不只是既有功能的组合）；连着核心幻想（不是贴上去的噱头）；影响玩法（不只是美术风格）。
- **常见错误**：把"像素风 + Roguelike"当钩子——这只是两个标签的叠加，过不了"and also"测试的好奇心检验。

### 4.5 Player Experience Analysis（MDA 框架）

- **是什么**：全文档方法论最重的一节。三张表：**目标审美**（玩家该感受到什么，8 选 N 排序）→ **关键动态**（希望玩家自发出现什么行为）→ **核心机制**（我们实际造哪 3–5 个系统）。
- **为什么**：这是"从情感倒推系统"的落地。先排"想让玩家感受到什么"，再问"什么行为能带来这种感受"，最后才问"什么机器能产生这种行为"。
- **要点**：8 个审美全部给优先级（1–8 或 N/A）；机制数量控制在 3–5 个；每一行"How We Deliver It"都要具体到可执行。
- **常见错误**：把顺序反过来（先想机制再凑体验）；8 个审美全填高优先级（等于没有优先级）。

### 4.6 Player Motivation Profile（玩家动机画像）

- **是什么**：三张小表：SDT 三需求（自主/胜任/联结各是核心、辅助还是最低）+ Bartle 四类型（勾选主打谁）+ 心流设计（入门曲线、难度爬坡、反馈清晰度、失败恢复）。
- **为什么**：解释玩家"为什么持续玩"。和 4.5 的区别：MDA 问"这次体验像什么"，动机问"他们为什么回来"。
- **要点**：SDT 三项各给"Core / Supporting / Minimal"评级并写怎么满足；失败恢复写清"失败是惩罚还是教育"。
- **常见错误**：心流四项只写"有教程、有难度"这类空话，没有可检验的描述。

### 4.7 Core Loop（核心循环）

- **是什么**：把"玩家在做什么"按四个时间尺度切开：**30 秒**（手在做什么）→ **5–15 分钟**（短期目标圈）→ **30–120 分钟**（一整局的样子）→ **长期成长**（数周追求什么）→ 附**回头钩子**四类。
- **为什么**：模板里最重要的一句警告在这里——30 秒循环**单独拿出来必须好玩**，否则任何成长系统都救不回来。这是"地基检查"。
- **要点**：每一层都要写具体动作；一整局要"有自然停点 + 有回来的理由"。
- **常见错误**：只写长期愿景（"玩家将建立自己的王国"），30 秒循环是空的。

### 4.8 Game Pillars（支柱）——本文档里的版本

- **是什么**：3–5 条不可协商的设计原则，每条 = 名称 + 一句话定义 + 一道设计测试；外加反支柱（"这游戏不是什么"）。
- **为什么**：开发中要做几千个小决定，支柱保证所有决定往同一个方向使劲。
- **要点**：数量卡死 3–5 条；每条必须有 Design Test；反支柱至少 3 条、且要"真的可能想做但被禁止"才有用（"不是赛车游戏"是废话，"不是开放世界"才有用）。
- **常见错误**：支柱写成口号（"好玩至上"——不可证伪、不约束任何事）。
- **特别注意**：这一节只是**种子**。它会被展开成独立的 `game-pillars.md`——第 6 节专门讲这件事。

### 4.9 Inspiration and References（灵感与参考）

- **是什么**：一张"参考游戏表"（从每款参考里拿什么、我们怎么改、验证了什么）+ 非游戏灵感（电影、书、音乐）。
- **为什么**：把"像谁"从模糊的感觉变成可检查的传承关系；非游戏灵感往往才是格调的真正来源。
- **常见错误**：只写游戏名不写"具体拿什么"。

### 4.10 Target Player Profile（目标玩家画像）

- **是什么**：把目标用户具体成一个真人：年龄、经验、时间、平台、正在玩的游戏、未满足的需求、劝退点。
- **为什么**：和 4.2 表里那行"Target Audience"呼应，把"18–35 岁中核玩家"展开成能做决定依据的人。
- **常见错误**：画像和 4.6 的玩家类型互相矛盾（画像说硬核动作玩家，动机表主打放松型）。

### 4.11 Technical Considerations（技术考量）

- **是什么**：推荐引擎、技术难点、美术风格与管线复杂度、音频、联网、内容量、程序化生成的一张评估表。
- **为什么**：给 `/setup-engine` 和后续架构阶段**喂初值**——注意这里是"考量"不是"决定"，真正的技术事实源是 `project.yaml` 的 `engine.*`。
- **常见错误**：在这里写死引擎版本然后不跑 `/setup-engine`（这份文档不驱动任何技术执行）。

### 4.12 Risks and Open Questions（风险与开放问题）

- **是什么**：四类风险（**设计**——可能不好玩；**技术**——可能做不出来；**市场**——可能卖不动；**范围**——可能做不完）+ 开放问题清单。
- **为什么**：把"我最怕什么"提前说出来。每条开放问题要附"打算用什么原型来回答"。
- **常见错误**：只写技术风险（最好写的那种）；开放问题没有验证方案。

### 4.13 MVP Definition（最小可行版本）

- **是什么**：一条**核心假设**（如"玩家觉得战斗-合成循环 30 分钟以上仍然有趣"）+ 必须做的最少功能 + **明确不做**的功能 + 四档范围表（MVP / Vertical Slice / Alpha / Full Vision）。
- **为什么**：MVP 只回答一个问题："**核心循环好玩吗？**"其他一切暂缓。范围档位是预算缩水时的降落伞。
- **常见错误**："Explicitly NOT in MVP"清单是空的——没有"明说不做"，范围一定会膨胀。

## 5. 设计思路：这份模板为什么长这样

把 13 节背后的六个原则提炼出来。理解了它们，不用背模板也能推断每一节为什么存在。

### 5.1 从感受倒推系统，而不是从功能正推

MDA 一节把顺序定死：**Aesthetics（想给玩家的感受）→ Dynamics（希望涌现的行为）→ Mechanics（要造的系统）**。多数失败项目的顺序恰好相反：先抄功能，再祈祷好玩。

### 5.2 每个主张都要可检验

| 主张 | 配套的检验方法 |
|---|---|
| 钩子真的独特 | "and also" 测试 |
| 支柱真的能裁决 | Design Test（一道真题） |
| MVP 值得做 | 单一核心假设 |
| 概念靠谱 | 四类风险 + 需原型回答的开放问题 |
| 30 秒循环好玩 | "单独拿出来也必须有趣"的地基测试 |

这和 `project.yaml` 的"枚举校验"、门禁的"PASS/FAIL"是同一种工程审美：**不许出现无法被证伪的话**。

### 5.3 时间尺度分层

核心循环拆成 30 秒 / 5–15 分钟 / 一整局 / 长期四层，强制设计者在每一层单独回答"好玩吗"。这防止两种经典病：只有宏观愿景（30 秒很无聊），或只有手感和成长（玩一小时不知为何而玩）。

### 5.4 "不做什么"和"做什么"同样重要

三处体现：Anti-Pillars（不许做的设计）、"Explicitly NOT in MVP"（不许进 MVP 的功能）、Scope Tiers（缩水时的档位）。**每个"不"都在保护一个"是"**——这是模板反复强调的原文。

### 5.5 它是决策文档，不是日记

文档头有 Status（Draft / Under Review / Approved），Next Steps 是一张指向 creative-director 审批、门禁、后续技能的清单。它存在的目的是**让"要不要继续做这个游戏"这个决定有据可依**，所以写完即冻结、变更走重新评审。

### 5.6 模板即引导

每个空括号旁的注释不是废话，而是**判据**（"10 秒测试"、"and also" 测试、AAA 范例）。/brainstorm 技能会逐阶段问答、逐节征求同意——模板、技能、门禁三者引用的是同一套标准。

## 6. 核心问题：为什么有了支柱章节，还要单独一份 game-pillars.md？

`game-concept.md` 里明明有完整的 "Game Pillars" 章节（支柱 + 反支柱 + 设计测试），项目却还提供 `game-pillars.md` 模板，产出 `design/gdd/game-pillars.md`。这不是重复，而是**两种角色、两个生命周期、两群读者**。用五组对比讲清：

### 6.1 种子 vs 展开

| | 概念文档里的支柱章节 | game-pillars.md |
|---|---|---|
| 篇幅 | 每支柱 2–3 行：名称 + 一句话定义 + 设计测试 | 每支柱一整节：定义 + 服务的 MDA 审美 + 设计测试 + **五部门影响表**（设计/美术/音频/叙事/工程各一行"这根支柱对你说……"）+ 服务示例 + **违反示例** |
| 反支柱 | 3 条左右，一句话理由 | 每条要写"会牺牲哪根支柱、会分散多少开发焦点" |
| 附加内容 | 无 | 支柱**冲突优先级排序**及裁决流程、SDT 三需求对齐检查、**情感曲线**（一局游戏的情绪起伏表）、11 条**验证清单** |

一句话：概念里的支柱是**摘要卡**，game-pillars.md 是**操作手册**。前者让人"知道"，后者让每个部门"知道怎么做、什么算违反"。

### 6.2 一次决策 vs 常备参考

- 概念文档在**概念阶段**被完整阅读：creative-director 审批、/design-review 完整性检查、概念门禁评估。批准后它基本**冻结**——它是历史决策的记录。
- game-pillars.md 在**整个开发全程**被反复加载：`/design-system` 写每个系统 GDD 前读它对齐方向，`/ux-design` 做交互设计读它，`/team-level` 做关卡读它，`/consistency-check` 查一致性读它，creative-director 仲裁"这功能该不该做"时读它（原话：读 pillars 是为了知道 **what's non-negotiable**——什么是不可让步的）。

模板自己的定位说明写得非常直白：

> *This document is the creative north star... is referenced by every design, art, audio, and narrative document in the project. Review quarterly or after major milestone pivots.*
> （本文档是创意北极星……被项目里每一份设计、美术、音频、叙事文档引用。每季度或重大转向后评审。）

### 6.3 上下文经济

这一点对 AI 流水线尤其实际：几十个技能需要支柱，但**不需要整份概念**。把支柱单独成文，意味着 `/design-system` 加载的是一份聚焦的小文档，而不是连 MVP、风险、技术考量一起拖进来。仓库对两份文档的治理也一视同仁——`gdd-structure-check.sh` 把 `game-concept.md`、`game-pillars.md`、`systems-index.md` 都归为 design/gdd/ 下的"治理文档"而非系统 GDD。

### 6.4 生命周期不同步

| | game-concept.md | game-pillars.md |
|---|---|---|
| 诞生 | /brainstorm 第 4 阶段产出种子 | 概念获批后建立（概念文档 Next Steps 第 3 条），由 creative-director 精炼 |
| 变更频率 | 批准后几乎不变 | **每季度或大转向后评审修订** |
| 版本管理 | Status 三态 | Version + Last Updated + Approved By |

### 6.5 关系是"回填"而不是"复制"

game-pillars.md 的 Next Steps 最后一条：

> *Add pillars to the game-concept document*（把支柱加回概念文档）

也就是数据流向是：**概念中的种子 → 展开成 pillars 文档 → 修订后把摘要回填概念**。概念文档里的支柱章节永远保持"摘要级"的简短，展开与裁决的权威在 game-pillars.md。

### 6.6 一个比喻

- `game-concept.md` = **立项的商业计划书**：论证"这栋楼为什么要盖、盖多大、卖给谁"。审批通过后锁进档案柜，偶尔翻阅。
- `game-pillars.md` = **贴在工地入口的施工原则牌**：每个工种进场前都要看一眼，遇到两难按它裁决，每季度校准一次。
- 各系统 GDD = **每层的施工图**。

计划书里当然也会写一句施工原则，但工人每天看的是门口那块牌子，不会天天重读计划书。

## 7. 心智模型：一张图记住所有关系

```text
        玩家感受 (Aesthetics/SDT/心流)
              ↑ 倒推
        概念文档 game-concept.md          【立项书·写一次】
        ├─ 是什么：Pitch / 身份 / 幻想 / 钩子
        ├─ 为什么好玩：MDA / 动机 / 核心循环
        ├─ 做多大：MVP / 范围档位 / 风险
        └─ 支柱(种子) ──────┐
                            ↓ 展开/回填
        支柱文档 game-pillars.md        【北极星·常备引用】
              ↓ 约束
        systems-index → 各系统 GDD → 架构 → 生产
```

三句话总结：

1. **概念文档回答"值不值得做"**——从感受倒推系统，每个主张可检验。
2. **支柱文档回答"每天怎么裁决"**——跨部门、可背诵、按季度校准。
3. **概念冻结，支柱常青**；摘要长在概念里，权威住在支柱里。

## 8. 常见误区与排错

| 症状 | 很可能的原因 | 处理 |
|---|---|---|
| /brainstorm 不问任何问题直接生成全文 | 走了非交互模式，或文档已存在被当作"续写" | 明确要求逐阶段问答；先看 `design/gdd/game-concept.md` 是否已存在 |
| 概念写得很美，门禁仍打回 | 缺可检验项：钩子没过 and-also、支柱没设计测试、MVP 没核心假设 | 对照第 5.2 节的检验表逐条补 |
| 支柱 8 条，人人背不出 | 违反 3–5 条上限 | 砍到 5 条以内，其余降级为"参考原则" |
| "Explicitly NOT in MVP" 是空的 | 没做减法 | 强制写至少 2 条，否则范围必膨胀 |
| 支柱文档和概念里的支柱不一致 | pillars 修订后没回填概念 | 按第 6.5 节流程把摘要同步回概念文档 |
| 各部门做出来的东西风格散架 | 只有设计支柱、没写五部门影响表 | 补 game-pillars.md 每根支柱的部门矩阵 |
| 概念里写死引擎版本，技术却不认 | 概念的"技术考量"只是建议 | 真相在 `project.yaml` 的 `engine.*`，跑 `/setup-engine` |
| Target Audience 写"所有人/玩家" | 画像缺失 | 按 4.10 的表格写具体的人 |

## 9. 自测：理解是否到位

1. 电梯陈述的"10 秒测试"检验的是什么？（答：没听说过这游戏的人能否 10 秒明白自己将干什么）
2. MDA 三个词的顺序为什么不能反？（答：从目标感受倒推涌现行为再倒推机制，反了就是"先造机器再祈祷好玩"）
3. 30 秒循环为什么是"地基"？（答：它单独不好玩，任何成长系统都救不回来）
4. 好支柱的四个标准？（答：可证伪、有约束力、跨部门、可背诵）
5. 反支柱为什么必须"真的可能想做"？（答：显然不会做的事写进去不约束任何决策）
6. MVP 只回答哪一个问题？（答：核心循环是否好玩）
7. 概念里的支柱章节和 game-pillars.md 谁是权威？（答：展开与裁决以 game-pillars.md 为准；概念里的是摘要，修订后回填）

## 附：一句话总结

`game-concept.md` 是用**玩家的感受**倒推**要造的系统**的立项书：它用 MDA 排体验、用核心循环验地基、用支柱立规矩、用 MVP 和范围档位控风险，让"这个游戏值不值得做"变成一个有据可依的决定。而它的支柱章节只是种子——真正天天被引用、按季度校准的"创意北极星"，住在 `game-pillars.md` 里：**概念管一时决策，支柱管全程裁决。**
