## 0. 先记住五句话

1. `game-pillars.md` 是项目的**创意北极星**：3–5 条不可协商的设计原则，被设计、美术、音频、叙事、工程每一个部门反复引用。
2. 它由**概念批准后的下一步**创建：`/brainstorm` 第 4 阶段先产出支柱"种子"，`creative-director`（创意总监代理）精炼展开，写入 `design/gdd/game-pillars.md`。
3. 它是**给人和 AI 代理读的治理文档**——没有解析器逐行解析它，脚本只把它当作 design/gdd/ 下的"治理文档"分类对待；真正逐字读它的是一个个技能和代理的上下文。
4. 它的维护节奏写在模板页脚：**每季度评审一次，重大转向后立即评审**；日常冲突靠文内的"优先级排序表"裁决，裁决不了才升级到创意总监修支柱本身。
5. 它和 `game-concept.md` 是**种子 → 展开 → 回填**的接力：概念里的支柱章节是摘要，这份是展开版；修订后要把摘要同步回概念文档。

## 1. 这份文档是什么，怎么被"读"

### 1.1 一句话定义

`game-pillars.md` 用一页（展开后数页）回答一个问题：**当几千个小决定互相打架时，什么说了算？**

它住在两个位置，角色不同：

| 位置 | 角色 |
|---|---|
| `.claude/docs/templates/game-pillars.md` | **模板**：带教学注释、判据和 AAA 范例的空壳 |
| `design/gdd/game-pillars.md` | **工作副本**：真实项目的支柱文档，被全流程引用 |

### 1.2 读写机制：和 project.yaml 完全不同的一类"配置"

这是初学者最容易混淆的一点，先讲清楚：

| 维度 | `project.yaml` | `game-pillars.md` |
|---|---|---|
| 谁解析 | `yaml-helper.sh` 逐键解析、校验枚举、带来源标签注入技能 | **没有任何解析器**。技能和代理用读文件的方式把它整篇（或按章节）装进上下文 |
| 值的形态 | 机器可校验的枚举/数字 | 自然语言的原则、例子、表格 |
| 脚本怎么用它 | 读具体键的值来分支行为 | 脚本**只认文件名**做分类（治理文档，不是系统 GDD），从不读内容 |
| 生效方式 | 解析结果驱动工具行为 | 作为上下文影响 LLM 代理的判断与产出 |
| 个人覆盖 | 白名单键可进 `project.local.yaml` | 无。它是团队级文档，进 Git |

一句话：**`project.yaml` 是机器执行的事实，`game-pillars.md` 是人和 AI 共同遵守的原则。** 它"生效"的方式是被引用、被对照、被复制进设计文档——不是被解析。

### 1.3 边界表

| 它是 | 它不是 |
|---|---|
| 全项目共享的设计裁决标准 | 功能清单或路线图 |
| 跨部门的约束（五个部门各有一行"这根支柱对你说……"） | 只约束玩法的规则书 |
| 带反支柱（"这游戏不是什么"）的范围防线 | 系统设计文档（那是各系统 GDD） |
| 活文档：按季度评审修订 | 一次写完就冻结的存档（概念文档才是冻结的） |
| creative-director 仲裁争议时的依据 | 仲裁者本身（仲裁者是 creative-director 代理） |

## 2. 谁在何时创建它

### 2.1 创建的完整链路

```text
/brainstorm 第 4 阶段（Pillars and boundaries）
  ├─ 起草 3–5 条支柱：名称 + 一句话定义 + 设计测试
  ├─ 起草 3+ 条反支柱："我们绝不做 X，因为会损害支柱 Y"
  ├─ 按 automation 档位与你确认后锁定
  └─ review_mode 为 full 时：走 CD-PILLARS 门禁
       └─ creative-director 代理审支柱（只评审、不编辑文件）
             ↓ 写入概念文档的支柱章节（种子）
概念获批（creative-director 审批 game-concept.md）
             ↓ 概念文档 Next Steps 第 3 条：
       "Create game pillars document (/design-review to validate)"
             ↓
从模板复制 → design/gdd/game-pillars.md
  ├─ 种子来自概念文档的支柱章节
  ├─ design-first 路线第 4 步：creative-director 代理精炼支柱
  ├─ creative-director 审批（Approved By 字段的默认值就是它）
  └─ 分发给各部门负责人签收（Next Steps 第 2 条）
```

要点：

- **种子在 brainstorm 里长出来**：`/brainstorm` 第 4 阶段专门负责支柱与边界，交互模式下会反复问你"这些支柱对味吗"，直到你选 `Lock these in`（锁定）。autonomous 模式则直接锁定并记录备选方案。
- **展开是概念批准之后的事**：概念文档的 Next Steps 明确把"创建支柱文档"列为审批之后的下一步，不是 brainstorm 当场写完。
- **精炼人是创意总监**：`/brainstorm` 的 design-first 推荐路线第 4 步写着"The creative-director agent: refine the pillars"。
- **写入要经过同意**：creative-director 代理的规则要求它在写任何文件前先问"May I write this to [filepath]?"——而且它的"免问例外"只覆盖 `production/`、`docs/`、`tests/` 下的新产物，`design/gdd/game-pillars.md` 不在其中，所以**修订支柱必须先征得你同意**。

### 2.2 什么情况下不会有这份文档

- 项目还在 Concept 阶段且 brainstorm 没跑到第 4 阶段：只有概念里的种子。
- 极简档（minimal rigor）的个人小项目：可以只用概念里的支柱章节，不建独立文档——代价是失去跨部门展开表和季度评审的约束。
- `/reverse-document` 逆向工程已有项目时，会从现有代码和文档反推出一份支柱文档。

## 3. 逐项讲解：每一项的内容、取值、默认值

先给一张总表。这份文档的"配置项"就是模板的 12 个组成部分；"默认值"指模板自带的预填内容。

| # | 部分 | 类型 | 默认值 / 预填内容 | 主要消费者 |
|---|---|---|---|---|
| 1 | Document Status | 元数据 | Version 1.0；Approved By: creative-director；Status: Draft | 人、评审流程 |
| 2 | What Are Game Pillars? | 教学序言（不填） | 四条好支柱判据 + 6 款 3A 游戏范例表 | 初学者、起草者 |
| 3 | Core Fantasy | 引用块 | 四条范例句式 | creative-director、全部门 |
| 4 | Target MDA Aesthetics | 排序表 | 8 种审美参考清单（Sensation…Submission） | 全部门 |
| 5 | The Pillars（1–3 必填，4–5 可选） | 结构化条目 | 每条六个子字段，见 3.5 | 全部门、各技能 |
| 6 | Anti-Pillars | 列表 | 无预填条目（要求至少 3 条） | 范围控制 |
| 7 | Pillar Conflict Resolution | 优先级表 + 流程 | 六步裁决流程全文预填 | creative-director、设计技能 |
| 8 | Player Motivation Alignment | SDT 三需求表 | 无预填（表头固定三行） | 设计评审 |
| 9 | Emotional Arc | 两张表 | 五阶段表头预填（Opening…Hook） | 叙事、关卡、音频 |
| 10 | Reference Games | 表 + 灵感 | 无预填条目 | 全部门 |
| 11 | Pillar Validation Checklist | 检查单 | **11 条判据全文预填** | 起草者、/design-review |
| 12 | Next Steps | 任务单 | 5 条预填（审批→分发→设计测试→2 周后首评→回填概念） | 起草者 |

### 3.1 Document Status（文档状态）

| 字段 | 取值 | 默认 | 说明 |
|---|---|---|---|
| Version | 语义化版本 | `1.0` | 每次季度评审有实质修改就 +0.1，大转向 +1.0 |
| Last Updated | 日期 | 建档日 | 与 Version 一起构成"活文档"的时间轴 |
| Approved By | 审批人 | `creative-director` | 模板默认就写死了创意总监——它是支柱的法定审批人 |
| Status | `Draft / Under Review / Approved` | `Draft` | 和概念文档同款三态 |

### 3.2 What Are Game Pillars?（教学序言）

这一节**不需要你填**。它是模板自带的教学内容，作用是让任何打开这份文档的人（包括新加入的 AI 代理）先建立判断力：

- **四条好支柱判据**：Falsifiable（可证伪——"好玩"不是支柱，"战斗奖励耐心而非莽撞"才是）、Constraining（有约束力——从没让你说过"不"的支柱太虚）、Cross-departmental（跨部门——只约束玩法不约束美术的支柱不完整）、Memorable（可背诵——团队背不出来就是太多太绕）。
- **6 款 3A 范例表**：战神、Hades、最后生还者、蔚蓝、空洞骑士、死亡细胞各自的支柱和"为什么有效"。比如战神的"一镜到底"激进到砍掉了标准的运镜工具——这才是有牙齿的支柱。

### 3.3 Core Fantasy（核心幻想）

- **取值**：一段话，回答"玩家在这里能成为谁、感受什么、什么是别处得不到的"。
- **为什么放在支柱前面**：模板要求每根支柱都能追溯回核心幻想（验证清单最后一条）。幻想是"为什么"，支柱是"怎么做才不离题"。
- **和概念文档的关系**：内容上就是概念文档 Core Fantasy 一节的延续/复述，两处应保持一致。

### 3.4 Target MDA Aesthetics（目标审美排序）

- **取值**：一张表，把 MDA 框架的 8 种审美（感官、幻想、叙事、挑战、交际、探索、表达、放松）排出 1、2、3……名次，不目标的可标 N/A 并写原因；每名附"我们怎么交付它"。
- **默认值**：8 种审美的定义清单是预填的参考（Hunicke, LeBlanc, Zubek 的 MDA 论文）。
- **规则**：**支柱集体要能交付前 2–3 名审美**（验证清单第 8 条）。这份排序和概念文档 MDA 一节的排序应一致——这里是"支柱视角"的重申。

### 3.5 The Pillars（支柱本体）——文档的核心

每根支柱是一个 `###` 小节，由**六个子字段**构成：

| 子字段 | 取值 | 写法要求 |
|---|---|---|
| One-Sentence Definition | 一句话定义 | 可证伪、具体到"两个人拿着它对同一个设计问题会得出同一结论" |
| Target Aesthetics Served | 服务的审美 | 从 3.4 的排序里挑（通常 1–2 个） |
| Design Test | 设计测试 | 一道真实的二选一："争论 X 还是 Y 时，这根支柱判我们选 __" |
| Department 表 | 五行：Game Design / Art / Audio / Narrative / Engineering | 每行两句："这根支柱对你说……" + 具体例子 |
| Serving This Pillar | 遵守示例 2+ 条 | 什么决定/功能体现了它 |
| Violating This Pillar | 违反示例 2+ 条 | 什么做法背叛了它——"我们绝不做的事" |

- **数量与默认**：Pillar 1–3 必填；Pillar 4、5 标注 Optional（可选）。验证清单第 1 条卡死 3–5 条。
- **为什么每个子字段都要"具体到例子"**：这份文档的读者有一半是 AI 代理。代理拿到"部门影响表 + 服务/违反示例"这种成对的正反例，比拿到抽象口号判断准确得多。这是它作为"AI 可用配置"的关键设计。

### 3.6 Anti-Pillars（反支柱）

- **取值**：`NOT [东西]: [为什么排除、会损害哪根支柱、会分散多少开发焦点]`，至少 3 条。
- **判据**（模板原话的意译）：好的反支柱是"团队真的可能想做"的事。"不是赛车游戏"是废话（显然不会做）；"不是开放世界"才有用（这个类型完全做得成，所以要明说不做）。
- **职责**：范围蔓延的第一道防线——**每个"不"都在保护某个"是"**。

### 3.7 Pillar Conflict Resolution（支柱冲突裁决）

两部分：

1. **优先级排序表**：把支柱按"核心幻想里最不可或缺的程度"排 1、2、3……每名写一句"它凭什么赢"。
2. **六步裁决流程**（模板全文预填，直接可用）：识别哪几根支柱在打架 → 查上面的排序 → 低优先级能部分满足就部分满足 → 不能则高优先级获胜 → **把决定和理由记进相关设计文档** → 如果冲突是根本性的（两根支柱不可调和），升级给 creative-director **考虑修订支柱本身**。

注意最后两步：普通冲突在文档内部就能裁决（这正是这张表存在的意义——不用每吵一次就惊动创意总监）；只有根本性冲突才触发"改支柱"这个大动作。

### 3.8 Player Motivation Alignment（玩家动机对齐）

- **取值**：一张三行表，SDT 三需求（自主 / 胜任 / 联结）各写"哪根支柱服务它 + 怎么服务"。
- **差距检查（Gap check）**：模板自带判据——三个需求若有一个没有任何支柱服务，就要考虑支柱集是否完整。三个都被满足的游戏有最强的持续游玩基础。
- **和概念文档的关系**：概念文档的动机画像回答"玩家为什么回来"；这里反向检查"我们的支柱有没有漏掉某类心理粮食"。

### 3.9 Emotional Arc（情感曲线）

两张表：

1. **单局情感曲线**：五行预填阶段——Opening（开头 0–5 分钟）→ Rising（爬升）→ Climax（高潮）→ Resolution（收尾）→ Hook（钩子）；每行写目标情绪、哪根支柱在驱动、什么机制在交付。
2. **长期情感演进**：一段话，说明前期 / 中期 / 后期 / 终局各自的感觉要有何不同。

- **为什么存在**：模板要求情感曲线是**刻意设计而非偶然**。它把"好玩"从主观词拆成一列可对照的检查点。

### 3.10 Reference Games（参考游戏）

- **取值**：一张表，每款参考游戏写"从它身上拿什么 / 我们怎么做不同 / 验证了哪根支柱"；外加非游戏灵感（电影、书、音乐——模板提醒：伟大的游戏从媒介之外汲取营养）。
- **和概念文档的关系**：概念文档的 Inspiration 一节是全量参考；这里只保留**和支柱互相验证**的那几款，每款必须挂到具体支柱上。

### 3.11 Pillar Validation Checklist（支柱验证清单）

**11 条判据全文预填**，建档时逐条勾选：数量 3–5；每条可证伪；有约束力；跨部门；有设计测试；反支柱 ≥3 条；有优先级排序；支柱集体交付前 2–3 名审美；SDT 三需求各有支柱服务；团队背得出来；每条可追溯回核心幻想。

这 11 条就是"什么算一份合格的支柱文档"的机器可对照定义——`/design-review` 评审时用的也是同一套标准。

### 3.12 Next Steps（下一步）

5 条预填任务：creative-director 审批 → 分发部门负责人签收 → **用真实的近期决策给每根支柱补设计测试** → 安排两周后的首次支柱评审 → **把支柱加回 game-concept 文档和 pitch 文档**（回填，见第 6 节）。

## 4. 读写机制详解：谁在读、怎么读

### 4.1 读者全景

| 读者 | 何时读 | 读来做什么 |
|---|---|---|
| `creative-director` 代理 | 任何战略决策、争议仲裁 | 原话：读 pillars 是为了知道 "what's non-negotiable"（什么不可让步） |
| `/design-system` | 写每个系统 GDD 前后的"可选读" | 新系统必须至少服务一根支柱；写完做支柱对齐检查 |
| `/ux-design` | 交互设计前 | 把交互方案约束在支柱范围内 |
| `/team-level` | 关卡设计时 | 关卡节奏对齐情感曲线与支柱 |
| `/map-systems` | 拆解概念为系统时 | 系统清单的优先级参考支柱 |
| `/gate-check` | 系统设计门禁 | 检查设计产出与支柱的一致性 |
| `/review-all-gdds`、`/consistency-check` | 跨文档评审 | 一致性比对的基准之一 |
| `/brainstorm` | 恢复会话时 | 与概念文档一起按章节续读，避免推倒重来 |
| `/reverse-document` | 逆向已有项目时 | 从代码反推支柱并写入此文档 |
| `project-stage-detect` | 阶段探测 | 它的存在是阶段判断的证据之一 |

### 4.2 脚本的治理方式：只认文件名，不读内容

三个脚本/钩子对它的处理完全一致——**分类为"治理文档"，排除出系统 GDD 流程**：

| 脚本/钩子 | 行为 |
|---|---|
| `gdd-structure-check.sh` | `not_a_system_gdd` 名单里有 `game-pillars.md`：不按系统 GDD 的结构标准检查它 |
| `review-scope.sh` | 从 `design/gdd/*.md` 里筛"系统 GDD"时排除它：改它不触发系统 GDD 的评审要求 |
| `validate-commit.sh` | 同一份排除名单：提交它不会被当成"改了系统设计"而要求完整证据链 |

这个设计很实用：**修订支柱是"改方向"，不是"改某个系统的设计"**——两件事的评审成本和证据要求完全不同。

### 4.3 一个重要推论

因为没有任何解析器，这份文档的"生效"完全依赖**引用它的技能是否真的把它装进上下文**。多数技能把它列为"存在则读"的可选输入——所以它是**影响力最大的软约束**：不读它的技能不会崩，但产出可能跑偏。这也是模板页脚强调"被每一份设计、美术、音频、叙事文档引用"的原因：引用密度就是它的执行力。

## 5. 维护：多久改一次、谁改、怎么改

### 5.1 维护节奏

| 时机 | 动作 | 依据 |
|---|---|---|
| 建档后 2 周 | 首次支柱评审 | Next Steps 第 4 条 |
| 每季度 | 例行评审 | 模板页脚："Review quarterly or after major milestone pivots" |
| 重大里程碑转向后 | 立即评审 | 同上 |
| 根本性支柱冲突 | 升级 creative-director，考虑修订支柱本身 | 冲突裁决流程第 6 步 |
| 战略决策之后 | 视需要做"pillar update" | creative-director 代理的决策工作流（写入前必须征得同意） |

### 5.2 修订的规矩

1. **版本留痕**：改内容就更新 Version 和 Last Updated，走 Draft → Approved 状态。
2. **决策级联**：冲突裁决流程第 5 步要求把"决定和理由"记进相关设计文档；涉及技术架构的重大决定走 ADR（`/architecture-decision`）。
3. **回填概念**：支柱修订后，把摘要同步回 `game-concept.md` 的支柱章节（Next Steps 最后一条），保持两份文档不打架。
4. **改它 ≠ 改系统设计**：脚本治理（4.2）保证修订支柱不触发系统 GDD 的完整评审链，改起来轻量。
5. **写入需同意**：creative-director 代理修订此文档前必须问过你（它的免问例外不覆盖 `design/` 目录）。

### 5.3 什么不该进这份文档

- 具体系统的设计参数（进该系统的 GDD）。
- 临时性的项目决定（进 ADR 或 sprint 文档）。
- 技术事实（进 `project.yaml`）。
- 个人偏好（这份文档没有本地覆盖层，改了就是改全团队的）。

## 6. 与 game-concept.md 的协作关系

### 6.1 接力的五个环节

```text
① 种子     /brainstorm 第 4 阶段 → 概念文档的"Game Pillars"章节
              （名称 + 一句话定义 + 设计测试，摘要级）
② 门禁     CD-PILLARS：creative-director 在 brainstorm 内审支柱草案
③ 审批     概念获批是建档的前置条件（概念 Next Steps 第 3 条）
④ 展开     种子 → design/gdd/game-pillars.md
              （五部门表、正反例、冲突排序、SDT、情感曲线、验证清单）
⑤ 回填     pillars Next Steps 最后一条：把支柱加回概念文档与 pitch
```

### 6.2 分工对比

| 维度 | game-concept.md | game-pillars.md |
|---|---|---|
| 角色 | 立项书：论证"值不值得做" | 北极星：裁决"每天怎么做" |
| 生命周期 | 批准后基本冻结 | 每季度评审、大转向修订 |
| 支柱形态 | 摘要（每条 2–3 行） | 展开（每条六个子字段 + 部门表） |
| 完整阅读者 | 概念阶段的审批与门禁 | 全程十几个技能与代理反复加载 |
| 权威方向 | 摘要 ← 回填 | 展开与裁决的权威在此 |
| 上下文成本 | 整份加载较重 | 小而聚焦，按需加载 |

### 6.3 协作读者

两者会被同一批流程**成对**消费：`/brainstorm` 恢复时按章节续读两份；`/gate-check` 系统设计门禁读两份；`review-scope.sh`、`gdd-structure-check.sh`、`validate-commit.sh` 把两份一同归入"治理文档"豁免名单；creative-director 同时是两份的审批人。

一句话总结协作关系：

> **概念文档里的支柱章节是"宪法条文摘编"，game-pillars.md 是"带司法解释的完整法典"——条文出自前者，裁决依据后者，修订后条文回填。**

## 7. 心智模型

- `game-concept.md` = 立项的商业计划书（锁进档案柜，偶尔翻阅）。
- `game-pillars.md` = **贴在工地入口的施工原则牌**：每个工种进场前看一眼，遇到两难按背后的优先级表裁决，每季度校准一次。
- 各系统 GDD = 每层的施工图（画图前要对照原则牌）。
- `project.yaml` = 登记表（机器执行的技术事实）。

判断"一件事该写进哪里"的口诀：

```text
是"为什么做这个游戏"吗？      → game-concept.md
是"怎么做才不离题"吗？        → game-pillars.md
是"这个系统具体怎么运作"吗？  → 该系统的 GDD
是"机器要反复读的事实"吗？    → project.yaml
```

## 8. 常见误区与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 支柱 8 条，代理引用时只提前 3 条 | 违反 3–5 上限，超出可背诵范围 | 砍到 5 条以内，其余降级为参考原则 |
| 部门表全是"遵守品牌调性"这类空话 | 缺具体例子，AI 无法据此判断 | 每行补一个具体的服务/违反示例 |
| 支柱之间从不起冲突 | 写得太和谐——好支柱应当"互相较劲" | 按 brainstorm 第 4 阶段的要求让支柱之间有张力 |
| 概念里的支柱和这份对不上 | 修订后没回填 | 按 6.1 第 ⑤ 环节同步摘要 |
| 每次争议都去问创意总监 | 没建冲突优先级表，或没先走六步流程 | 填 3.7 的排序表，按流程前四步自行裁决 |
| 改了支柱后系统 GDD 没变化 | 下游技能把它当"可选读"，没被触发 | 对关键系统重跑 /design-system 或 /consistency-check |
| 想给支柱加本地个人版 | 此文档无覆盖机制 | 不存在；要么改团队版（走评审），要么写进 ADR |
| 反支柱形同虚设 | 写的是显然不会做的事 | 换成"真的可能想做但被禁止"的项 |

## 9. 自测

1. 好支柱的四条判据是什么？（可证伪、有约束力、跨部门、可背诵）
2. 两根支柱打架，前几步在文档内部解决？（四步：识别→查表→部分满足→高优先级胜；第五步记录，第六步才升级）
3. 谁是支柱的法定审批人？（creative-director，模板 Document Status 默认值）
4. 脚本会解析支柱内容吗？（不会，只按文件名归类为治理文档）
5. 支柱修订后必须做什么同步？（回填 game-concept.md 与 pitch 文档）
6. 建档后第一次评审在什么时候？（两周后）
7. SDT 差距检查查什么？（三个心理需求是否各有至少一根支柱服务）
